# 开发经验（错误记录）

> 用途：记录每次开发/调试中出现的所有错误——现象 / 根因 / 修复 / 教训，防重复踩坑。
> 规则来源：CLAUDE.md「规则 D：出错必记录」（2026-08-11 用户要求）。
> 前端视觉/动画专项经验见《前端视觉与动画工程经验.md》。

## 一、前端渲染类

### 1. WXML `<text>` 内嵌 `<view>` → 编译错误页面打不开
- **现象**：知识图谱页白屏，navigateTo timeout
- **根因**：图例写 `<text><view class="sw"></view>已掌握</text>`，text 组件禁止嵌套 view
- **修复**：图例改 `<view class="lg">` 包裹
- **教训**：页面打不开先怀疑 WXML 编译错误（JS 语法 OK ≠ 页面可用）

### 2. `conic-gradient` / `mask` / opacity 动画在小程序渲染不可靠
- **现象**：掌握度环变白节点、节点全透明（依赖 opacity:0 动画）
- **根因**：小程序渲染层对浏览器 CSS 特性支持不稳，失败静默降级
- **修复**：掌握度环用 border 色环；动画只动 transform 不碰 opacity
- **教训**：小程序禁用 conic/mask/依赖 opacity 的动画

### 3. 合成节点（单元/小节）名字不显示
- **现象**：知识图谱「数学」页节点只有空心圆没有字
- **根因**：nodeView 的 `label` 条件排除了 `node.synthetic`，而合成节点名字全 >5 字走 label 分支 → 圆内外都无字
- **修复**：`label: (!isCenter && (longName || node.synthetic)) ? node.name : ''`
- **教训**：改显示条件时检查所有节点类型（synthetic/普通/长名/短名），别只覆盖一种

### 4. 节点数量过多 → 认知超载
- **现象**：知识点层 10+ 个卫星节点环绕过挤
- **依据**：工作记忆容量 7±2（Miller）、认知负荷理论（Sweller）——一屏 >8 元素理解下降
- **修复**：单屏卫星上限 8 个，超出折叠为「+N 更多」，点开展开全部
- **教训**：图谱/列表类 UI 默认遵守 7±2 组块化

### 5. Canvas 尺寸用 rpx 预计算 → 线节点错位
- **修复**：onReady 实测 boundingClientRect，Canvas 与节点共用坐标系

### 6. 开发者工具 navigateTo 全超时 → 先重启工具
- **修复**：模拟器卡死时重启微信开发者工具，不是改页面

### 13. 改错了页面：knowledge-map 有新 UI，用户打开的是 tab「图谱」graph
- **现象**：用户说「写成生产级」后编译仍是旧版放射图+Canvas
- **根因**：真正入口是 `app.json` tabBar → `pages/graph/graph`；`pages/knowledge-map` 只从 dimension-detail 的 `navigateTo` 进入，日常几乎打不开。生产化只改了 knowledge-map，没改 graph
- **修复**：把新版目录列表+演化链同步到 `pages/graph`，并保留 tab 特性（无返回键、根层不 navigateBack、底部 tabBar 占位）
- **教训**：改「知识图谱」前必须确认用户实际打开的是哪一页——查 `app.json` tabBar + 全部 `navigateTo`/`switchTab` 入口，不要假设同名页面就是入口

### 20. 小程序 katex（@rojer/katex-mini）构建 npm 后 wxss 字体内联被替换为 CDN 远程 URL
- **现象**：公式渲染缺字体（显示方块）；构建产物 `miniprogram_npm/@rojer/katex-mini/index.wxss` 只有 26KB，@font-face 指向 `cdnjs.cloudflare.com` 远程 URL
- **根因**：微信「构建 npm」改写 wxss，把源包 `dist/index.wxss`（1.4MB，字体 base64 内联）替换成 CDN 远程字体引用；小程序 WXSS 的 @font-face 不支持远程 URL，且 cdnjs 域名被墙加载必失败
- **修复**：`app.wxss` 不 import 构建产物 wxss，改用 `miniprogram/libs/katex-mini/index.wxss`（与源包 `dist/index.wxss` 逐字节一致，`cmp` 验证，base64 自包含）
- **教训**：构建 npm 产物不能盲目信任，wxss/字体类资源构建后要核对内容；npm 包内联资源（base64）在构建时可能被改写，字体类必须用自包含方案

### 21. katex-mini 解析选项是 `throwError`，不是 katex 原生的 `throwOnError`
- **现象**：页面用 `throwOnError: true` 期望非法公式抛错，实际不抛（错误被渲染成红色文本而非被 catch）
- **根因**：katex-mini 的包装只认自己的选项 `throwError`（官方 README），katex 原生 `throwOnError` 被忽略
- **修复**：用 `throwError: true` + try/catch 容错，非法公式正常抛错并展示错误提示
- **教训**：第三方 mini 包的 API 选项以官方 README 为准，不要想当然套用上游库的选项名

### 22. katex-mini `renderMathInText` 默认不识别 `$...$`
- **现象**：混排文本里 `$f(x)=x^2$` 原样显示，只有 `$$...$$` 被渲染
- **根因**：默认 delimiters 是 `$$`、`\(...\)`、`\[...\]` 和若干 `begin{equation}`，不含单 `$`
- **修复**：`utils/latex.js` 的 `renderMathText` 传入自定义 delimiters（`$$` 优先，再 `$`）
- **教训**：项目约定 `$`/`$$` 时，封装层必须显式覆盖默认 delimiters；纯文本无公式时返回值可能是 string，需规范成 nodes 数组

### 23. 登录慢：无用的 wx.login + 头像上传堵门 + 忽略本地 openid 缓存
- **现象**：每次启动都进登录页，点「进入学习」要等很久
- **根因**：① 首页是 login 且不读本地 `userInfo._openid` 缓存 ② `wx.login` 拿了 code 却不传云函数（CloudBase 上下文自带 OPENID）③ 头像 `uploadFile` 串行挡在 `userLogin` 前
- **修复**：启动页改 index；有 `_openid+nickName` 缓存直接进首页；去掉 `wx.login`；先 `userLogin` 再异步上传头像
- **教训**：CloudBase 身份用 openid，前端缓存 `_openid` 即可快进；别把可后台做的上传放进登录关键路径

### 24. 复核页每题痕迹都是整份视觉报告（串题）
- **现象**：展开「做题痕迹」时，每道题都看到全部题目的痕迹/转录
- **根因**：`diagnose` 落库 `traceReport: item.traceReport || vr.report`，拆题未给出单题痕迹时回退成整份视觉报告
- **修复**：禁止整份回退；视觉/拆题 prompt 要求按「## 第N题」分组；空痕迹时按题号从全文摘录，再不行给空串
- **教训**：多题共用上游文档时，禁止用整份原文做单题字段兜底

### 25. katex 分包后公式「挤一块」：定制前缀版 katex.min.js 与标准 wxss class 不匹配（2026-08-26）
- **现象**：公式渲染出结构但布局挤、字体效果差；主包时代正常、分包后坏了
- **根因**：pack 分支的 `libs/katex/katex.min.js` 是「所有 class 加 `katex-` 前缀」的定制版（输出 `katex-base`/`katex-strut`），而配套 wxss 是标准版规则（`.katex .base`）→ class 匹配不上 → `position/white-space/display` 等布局样式全部失效
- **修复**：换回标准版 katex（`node_modules/katex/dist/katex.js`），JS 输出标准 `base` 类，与 `.katex .base` wxss 匹配；node 对比两种版本输出（`JSON.stringify(nodes)` 找 class 差异）快速定位
- **教训**：katex-mini 的 JS 与 wxss 必须同版本配套；本地化 npm 包时不能只拷 JS——class 前缀类定制必须同步换 wxss；症状「渲染出来但丑/挤」优先怀疑 class 不匹配

### 26. 小程序字体加载：分包内字体文件在模拟器不可靠，base64 内联最稳（2026-08-26）
- **现象**：分包 woff2 字体 → `readFileSync` 报 `permission denied`（主包代码读分包文件被权限隔离）、渲染层字体请求 500、`loadFontFace` 本地路径失败
- **根因**：微信对分包文件的跨包访问限制（主包 JS 读分包文件拒绝）+ 模拟器渲染层加载分包字体 bug
- **修复**：字体 base64 内联到**全局** wxss（`miniprogram/styles/katex.wxss` 1.4MB），零文件请求，模拟器/真机都稳定；代价是主包 +1.4MB（预览/真机调试 OK，上线上传若超 2MB 把 latex-demo 演示页移出分包即可）
- **教训**：小程序字体优先 base64 内联；主包代码无法 `readFileSync` 分包文件（权限隔离）；rich-text 节点 class 只匹配**全局样式**（app.wxss），分包页面 wxss 的样式对 rich-text 内部节点不生效

### 27. 新版开发者工具 babel 转译报 `module '@babel/runtime/helpers/xxx' is not defined`（2026-08-26）
- **现象**：含 `for...of`/数组展开的文件编译报错；`Unexpected token 'export'`（ESM 文件）；graph.js 源码未改却报错
- **根因**：新版工具（2.01.x）ES6 转译把 babel 辅助函数抽取到 `@babel/runtime`，但 `babelSetting.outputPath` 为空字符串时工具不生成该目录 → helper require 落空；关掉 es6 转译又导致 ESM 文件（towxml 的 highlight.js 语言模块）无法转译
- **修复**：`babelSetting.outputPath` 显式设为 `"@babel/runtime"`（工具自动生成 helper 目录）；es6/enhance 保持 true（项目含 ESM 文件必须转译）
- **教训**：`babelSetting.outputPath` 不要留空；graph.js 源码没变却报 babel 错误 = 工具版本/编译配置问题，先查 babelSetting 而非源码

## 二、诊断管线 / LLM 调用类

### 7. thinking 开 + 难题 = content 全空（死锁）
- **现象**：deepseek-v4-flash thinking（high/max）+ 难题，content 空 ×8 次（含 json_object/流式/24000 token）
- **根因**：模型"想不完"——reasoning 6.4 万字符仍在思考，永不进入 content 输出（能力边界）
- **修复**：D 判定用 thinking disabled；分析类任务待实测
- **教训**：长思考 ≠ 高质量，难题思考会死锁；「宁等」等不到，是 API 行为

### 8. disabled 直接判难度 = 稳定地错（低估）
- **现象**：难题直接判档 D=0.76（真实 0.92）
- **修复**：学生视角体验（模拟学生卡顿）+ 我方 L1-L11 标尺判档 → 0.92 命中
- **教训**：难度是体验属性，学生视角比冷静分析准；模型数步骤会低估构造难度

### 9. 难度评分随"评估方式"漂移（视角决定难度）
- **现象**：同题：直接判 0.76 / 学生视角 9分 / 自拟标准 7.2 / 学生视角+标尺 0.92
- **修复**：定稿 = 学生视角 + 我方标尺 + temperature 0.2 + 同题缓存（3 次平均）
- **教训**：评估类任务先定"视角"，视角错全盘错

### 10. 脚本多次 python 字符串替换 → 语法坏
- **现象**：/tmp 脚本改几次后 SyntaxError（单引号/反引号/正则冲突）
- **修复**：直接重写整个文件（cat heredoc），不再累积 patch
- **教训**：临时脚本改动超过 2 处就重写，别叠加替换

## 三、通用

### 11. 删除函数漏删调用 → ReferenceError 白屏
- **现象**：删 gradOf 定义，nodeView 里调用残留 → 页面空白
- **修复**：删函数前 grep 全项目调用点
- **教训**：删除代码 = 查调用链

### 12. setData 异步时序误判
- **现象**：evaluate 同步读 data 拿到旧值，误以为渲染 bug
- **修复**：延时/回调后再读；实际功能正常
- **教训**：自动化验证要等 setData 完成，别把时序当 bug

### 13. 本地 knowledge-graph 文件与云端 knowledge_nodes 不一致
- **现象**：回填掌握度时用本地 `knowledge-graph/nodes/*.json` 匹配节点名，「基本不等式」匹配失败——本地 `math_10_ch2_s2_002` 叫「基本不等式定义」，云端叫「基本不等式」
- **根因**：云端数据被另行修正过（359 条 vs 本地 357 条），本地文件不是权威源
- **修复**：回填/匹配以云端 knowledge_nodes 为准（judgeOne 运行时查云端天然正确；本地脚本需手动补云端修正映射）
- **教训**：任何依赖节点名/节点清单的本地脚本，先比对云端，别假设本地文件=云端

### 14. AI 判定 knowledgeNodeName 是句子式描述，精确匹配节点名必失败
- **现象**：17 条已判题 knowledgeNodeName（如「集合的子集与真子集」「集合的包含关系」）对节点名（「子集」「真子集」）精确匹配率 0%
- **修复**：judgeOne 掌握度匹配改为「精确 → 子串命中取最长名（最具体）」
- **教训**：AI 自由文本关联知识节点必须容错匹配；子串最长命中是够用的近似，终极方案是二次复核让用户选节点

### 15. 云函数模块级函数引用未定义 `event`（新写 ragService 自查发现）
- **现象**：getUser() 函数体内写 `event && event.userId`，但 getUser 是模块级函数，无 event 参数——运行时必然 ReferenceError
- **根因**：从入口处复制身份逻辑到独立函数时残留了 event 引用
- **修复**：删除死函数，身份逻辑内联到入口
- **教训**：新写代码自查一遍「未定义引用 / 未使用函数」；node --check 只查语法不查语义

### 16. mastery_logs 的 isCorrect 存在两种存储格式（读侧必须兼容）
- **现象**：getErrorPattern 用数据库 where 过滤 `{ isCorrect: false }`，只匹配到顶层字段格式的记录
- **根因**：dispute 写的 score_poc 记录 isCorrect 存在 `report.isCorrect` 对象内（无顶层字段），judgeOne 新写的 diagnose_v1 才有顶层字段——同一集合两种格式
- **修复**：拉全量后内存过滤 + 统一 logIsCorrect() 兼容两种格式
- **教训**：跨云函数写同一集合时字段格式必须统一，或读侧兼容两种；数据库 where 过滤会把缺失字段的记录静默排除

### 17. unit_progress 集合从未创建 → A 维度静默失败（2026-08-17 实测揪出）
- **现象**：judgeOne 判定日志 `collection not exists: unit_progress`，但整体返回 success
- **根因**：A 维度代码一直查 unit_progress 集合，集合从未创建；外层 try/catch 吞掉错误只 console.error，主流程继续 → 判定成功但 A 更新全丢
- **修复**：MCP 创建 unit_progress 集合
- **教训**：try/catch 包「非核心更新」时，错误日志不能只看不看——用 MCP 查集合是否存在验证「以为在跑的功能」真的在写数据

### 18. pOk 作用域错误 → RAG 记录写入静默失败（2026-08-17 实测揪出）
- **现象**：mastery_logs RAG 记录（diagnose_v1）从没写入过，日志 `pOk is not defined`
- **根因**：RAG 写入块在掌握度 try/catch 之外，引用 try 内 const pOk——ReferenceError；node --check 只查语法不查作用域，部署不报错
- **修复**：pOk 提升为函数级 let（同 mainNodeId 处理）
- **教训**：跨 try 块共享变量必须提升作用域；改代码后要真机/真数据验证写入（不是只看返回 code=0）

### 19. MCP invoke 测不了长任务云函数（2026-08-17 reportService）
- **现象**：reportService（Flash 多轮生成 + 工具循环，耗时可能 60-120s）用 MCP invokeFunction 稳定 `network timeout at scf.tencentcloudapi.com`；reports 集合无记录
- **根因**：MCP→SCF API 的等待窗口 < 函数真实生成耗时；短函数（statService/judgeOne）秒回正常
- **修复**：① 加 `action=ping` 健康检查（秒回）区分「函数挂了」vs「生成慢」② 完整生成验证改由用户在小程序端触发（wx.cloud.callFunction 客户端等待窗口大）
- **教训**：新云函数先 ping 确认活着，再区分「慢」还是「坏」；长任务（AI 多轮生成）的端到端验证必须走真实客户端，MCP invoke 只适合快速入口

### 20. 拍照页 progress-mask 与 wx.showToast 叠层（2026-08-25）
- **现象**：识别失败/提交失败时，自定义进度遮罩与系统 toast 同时出现，文案互相挡住
- **根因**：`analyzing/submitting` 仍为 true 或刚关遮罩时调用 `wx.showToast`（如「未识别到题目」）
- **修复**：流水线错误改 `pipelineError` 页内条（知道了/重试）；遮罩期间不再 showToast；选图前校验仍可用 toast
- **教训**：有自定义全屏 loading 时，失败态用页内状态，勿叠系统 toast/Loading

### 21. 报告生成干等无进度 / 超时文案不清（2026-08-25）
- **现象**：进报告页长时间只转圈；超时后错误信息难懂；异议重生成用 `wx.showLoading` 易与 toast 叠层
- **根因**：云函数无流式进度；客户端 timeout 默认偏短；失败态未统一可重试
- **修复**：报告页按耗时推进阶段列表 + 已等待秒数（不做百分比假进度条）；`callFunction` timeout 180s；超时文案引导重试；异议改页内 `regenerating` 遮罩
- **教训**：长 AI 任务前端用「阶段可视化 + 可重试」即可，百分比假进度易误导；叠层优先页内状态，少用系统 Loading

### 22. 复核页参数两种风格 / 每题五维（2026-08-25）
- **现象**：参数区同时出现人话格子与 `P=`/`η=` 工程符号；用户明确「每道题不要显示五维参数」
- **根因**：`listQuestions` 下发 `fiveDim`/`P`/`η`；WXML 仍渲染 P/η；`.p-val.dims` 残留五维样式
- **修复**：复核 UI 只保留难度/知识点/对错/归因；接口不下发 fiveDim/P/η；补回 `transcriptionReviewed`/`paramsReviewed`；删 `.dims`
- **教训**：学生端参数展示与内部工程量（五维/P/η）隔离；list 接口按展示白名单出字段
### 23. 真机调试 80051：主包超 2MB → katex 本地字体 + 分包（2026-08-25）
- **现象**：自动真机调试 `source size 2098KB exceed max limit 2MB`（错误码 80051）
- **根因**：① `libs/katex-mini/index.wxss` base64 内嵌字体约 1.4MB；② towxml/katex 挂在主包并由 `app.js`/`app.wxss` 全局引入
- **修复**：katex 改本地 woff2；建 `packageDiagnose`（review/report/latex-demo + towxml + katex）、`packageExtra`（logs/admin 等）；主包去掉 towxml/katex 全局引入；跳转路径改为 `/packageDiagnose/...`

### 41. bash 沙箱静默丢弃 cp -R：目录复制「成功」却不落盘
- **现象**：`cp -R` 复制插件目录（到 /tmp 或工作区均同）exit 0、`-v` 打印了 `src -> dst`，但目标当场不存在或只剩空壳；单文件 cp 与 `cat >` 重定向完全正常

- **教训**：沙箱环境「命令成功」≠「落盘成功」；目录级复制必须验证关键文件存在，不能信退出码

### 51. 合成学生痕迹：字符串比对判不了数学等价 + 字符串级约束会被模型"满足字面"绕过（2026-09-13）
- **现象**：造评测用的学生痕迹（`scripts/synth-traces.mjs`），要求 `wrong` 角色"答案必须与正确答案不同"。模型交了 `S_n=2/9-2/9·4^n+(n/3)·2^{2n+1}`，官方答案是 `((3n-1)2^{2n+1}+2)/9` —— **字符串不同但数值代入 n=1..5 完全相等**，即根本没做错；反过来 `alt`（野路子做对）被我第一版检查器误报"不一致"（只是多了 `$` 和 `；`）
- **根因**：① 约束写在**字符串层面**（"答案必须不同"），模型就换个等价写法满足字面，不满足意图；② 我第一版质检用 `replace(/\s/g,'')` 比字符串，**数学等价 ≠ 字符串相等**，既误报又漏报；③ 概念型填空题（如"随机模拟法求积分的表达式"）**天然没有出错空间**，模型诚实回复 `errorStep: 无（本题作答正确）`
- **修复**：① 约束改成**语义级 + 可验证口径**——"把 n=1 代进去，studentAnswer 的数值必须与正确答案不同"；② 质检改成**第二次模型判定**（`--audit` 可重判全库），结果写 `verify.equivalent`，可疑的打 `quality` 标记；③ **消费约定：忽略带 `quality` 的条目**（数据不删，留证据）；④ 概念型填空只跑 correct/blank
- **教训**：① **"判对错"这类语义判断，代码只能做形式检查，必须引入判定环节**（这也是本项目 D3 存在的理由）；② prompt 约束要写成**可执行验证的口径**（给具体代入值），写"必须不同"等于把判断交给模型的字面理解；③ 数据集的正确性要在**入库时**验，不能等消费时才发现——毒数据混进评测集会污染后续所有结论
- **同时踩的两个自伤 bug（记录备查）**：`reduce((a,x)=>..., a)` 漏传初始值 → `a is not defined`；role 规格里定义了 `answerHint` 却**从未注入 prompt**（死字段），导致约束形同虚设——**定义字段后必须验证它真的被用到**

### 52. 拍照上传链路：离开小程序再回来报英文错 —— 云能力结果有 TTL，且原始错误被直接展示给学生（2026-09-13）
- **现象**：拍照页点「完成，开始分析」后，在进度遮罩期间离开（尤其把**整个小程序切后台**），回来会看到一段英文报错。**有概率触发**，取决于离开的时机。
- **日志实证**（`upload_logs`：拍照页长按标题「拍照诊断」复制 / 我的 → 运行日志）：
  - `2026-09-01`：`cloud.uploadFile:fail undefined . uploadFile:fail interrupted`（上传阶段卡 78s 后被中断，2 张图）
  - `2026-09-07`：`-404010 result expired`，**微信自带 trace**：`18:11:38 start → 18:11:42 app hide → 18:14:5 app show → poll result expired`（诊断耗时 147s）
  - `2026-09-07`：`-501002 resource server timeout | ESOCKETTIMEDOUT`（诊断耗时 65s）
  - 对照：正常诊断 20–53s 全部成功 → **失败案例都远超正常耗时区间**
- **根因（三层，缺一不可）**：
  1. **微信小程序切后台会限制云能力**（平台行为，非代码 bug）：`wx.cloud.uploadFile` 直接中断；`wx.cloud.callFunction` 的**结果有 TTL**，后台待久了客户端就再也取不到，报 `-404010 result expired`。**云函数在服务端其实跑完了。**
  2. **`catch` 把 `e.message` 原始英文直接塞进 `pipelineError`** 展示给学生 —— 违反本项目自己的规范：详细设计 §7 早已规定「上传失败→"上传失败，请重试"」「诊断超时→"分析超时，请重试"」「网络断开→"请检查网络连接"」，§47 原则 3 也写了「报错文案面向学生，不面向开发者」。**规范写了，实现从未跟上。**
  3. 拍照页**没有 `onHide`/`onUnload`**（详细设计 §6 写了「onUnload → 清理临时照片数据」，同样没实现）→ 链路日志里**无法区分"离开的是页面还是整个小程序"**，排查只能靠猜。
- **修复（`miniprogram/pages/photo/photo.js` + `miniprogram/app.js`）**：
  1. **抢救**：诊断报 `-404010 / -501002 / timeout` 时**不再直接报错**，改为轮询 `judgeOne action:listQuestions`（5s 一次，最长 3 分钟）→ 题目出现就跳复核页。**判据取「连续两次轮询到相同且非空的题目数」**——因为 `diagnose` 是「先逐题 `questions.add`、最后才 `batches.update({totalQuestions})`」，只看"非空"会拿到写了一半的残缺题目。**不需要改云函数、不需要部署。**
  2. **文案人话化**：`humanizeSubmitError()` 分四类（上传中断 / 结果过期 / 超时 / 其他）；原始错误仍由 `log.append('submit_fail', {error})` 落日志备查。照片列表不重置（符合 §7）。
  3. **日志补生命周期**：`app.js` 的 `onShow/onHide` + 拍照页的 `onHide/onUnload` 各记一条（带 `submitting/analyzing`）→ 下次直接有据可查。
  4. **顺手修**：`wx.compressImage` 参数 `compressHeight` → `compressedHeight`（§49 已记过参数名不对称，这里漏改了 `ed`）。
- **⚠️ 不要"修掉"离开后继续跑**：用户明确要的是「**离开也继续跑**」。
  - **离开页面**（点 tab / 跳别的页，小程序仍在前台）→ 逻辑层继续执行，**本来就能跑完** ✅
  - **切后台（app hide）** → 平台限制云能力 ❌
  - 所以 `onHide/onUnload` **只能留痕，绝不能中止链路**；也不要做"离开就中止"或"锁住不许离开"。
- **约束（决定方案形态）**：`diagnose/index.js:236` 有 `if (b.data.status !== 'pending') return fail(40003, '批次已诊断，请勿重复提交')` → **恢复只能靠轮询，不能靠重调 diagnose**。
- **教训**：① 平台级限制（切后台中断云能力）在 App 层**无法消除**，只能做成「优雅降级 + 可恢复」；② **详细设计里写了的错误处理必须真的去实现**，否则规范形同虚设、bug 复发；③ 长耗时云调用要按「**结果可丢失**」设计——**完成判据要落在数据库状态上，而不是函数返回值**（本项目 `report.js` 的 `pollReportUntilReady` 就是这个思路）；④ 排查这类"有概率"的问题，**先给链路日志补上生命周期事件**，否则连"离开的是页面还是小程序"都分不清。

### 53. 历史报告真机「点了一条没反应」——列表与详情同页 + navigateTo 叠栈超 10 层，且无 fail 回调（2026-09-15）

> ⚠️ **2026-09-17 更正：本节「根因」判断错误，修复无效（已上开发版 #21 真机复测仍点不开）。** 真因见 §54：`report.wxml` 的 `data-batchId` 驼峰被微信自动转小写为 `dataset.batchid`，`openBatch` 读 `dataset.batchId` 得 `undefined`，在 `if (!batchId) return;` 处**静默早退**，根本走不到导航 API——所以改 `redirectTo`、加 `fail` 回调都不会触发。以下原文保留作反面教材。

- **现象**：真机（开发工具不复现）从「我的 → 学习报告」进入历史列表，列表**显示完全正常**（日期 + 对/总题数都对），但**点任意一条都没反应**——不跳转、无 toast、**无红字**；**所有**历史条目一律点不动。对照：拍照诊断完自动进报告 **能正常打开**。
- **排查过程**（按"排除法"逐步锁死，值得复用）：
  1. 先怀疑读取链路（`listByUser` / `getByBatch`）——被"列表数字正常"证伪：若 `listByUser` 异常，`loadBatchList` 会 `catch → noReport`，列表根本出不来；数字正常也说明 v2 映射（`report.questions` 计数）没问题，顺带排除了"老记录缺 `batchId` 字段"的假设。
  2. 再怀疑云函数报错——"无红字 + 拍照链路能开"，且两链路走同一个 `reportService`，证伪。
  3. 锁定 `openBatch`（`report.js`）：链路只有 3 行，`if (!batchId) return;` 与 `wx.navigateTo({...})` **都没有失败可见性**——`navigateTo` 被系统拒绝时**静默失败**。用"拍照链路能开"区分开：数据/路由/分包都没问题 → 只剩 `navigateTo` 自身被拒。
- **根因**：**列表视图与详情视图是同一个页面**（`report.js` 用 `view: 'list' / 'report'` 两态复用，`onLoad` 按有无 `batchId` 分流），而 `openBatch` 却用 `navigateTo` **再压一个自己**。小程序页面栈上限 **10 层**，反复"进列表→点报告→返回"几次后栈满，之后 `navigateTo` 一律被拒；又因为**没写 `fail` 回调**，失败完全无声 → "点了没反应"。
- **修复**（`miniprogram/packageDiagnose/pages/report/report.js` 只改 `openBatch` 一个函数）：`navigateTo` → **`redirectTo`**（列表→详情是同一页面的视图切换，不该叠栈，替换当前页即根治）；并补 **`fail` 回调**：`console.error` + `wx.showModal` 把错误弹出来（真机连不上 console，必须让失败可见）。
- **教训**：
  ① **同一页面承担"列表/详情"两种视图时，列表→详情必须用 `redirectTo`**（或页面内切视图），用 `navigateTo` 会在栈上累积自身直到 10 层上限；
  ② **`navigateTo` / `switchTab` 等导航 API 一律要带 `fail` 回调**——静默失败在真机上无法排查，用户只会说"点了没反应"；
  ③ 排查"点击无反应"先做**同类操作对照**：本项目"拍照→报告"与"列表→报告"结果不同，一步就把范围从"数据/云函数"缩到"导航"；
  ④ **开发工具与真机行为可能不同**（真机页面栈、分包加载更严格），真机问题必须真机验证，别在工具里复现不出来就搁置。

### 54. §53 的真实根因：`data-batchId` 驼峰被微信转小写 → `dataset.batchId` 取不到 → 静默早退（2026-09-17）
- **现象**：§53 的 `redirectTo` 修复上了开发版（CI run #21 / commit `2bcf114`，workflow success）后，真机「我的 → 学习报告」点任意一条**仍然没反应**，也没有弹上次加的 `fail` 弹窗。
- **真因**：`miniprogram/packageDiagnose/pages/report/report.wxml:43` 写的是 `data-batchId="{{item.batchId}}"`。微信对 `data-*` 有硬规则——**连字符转驼峰，大写字母自动转小写**（官方例：`data-elementType` → `dataset.elementtype`）。因此事件里只有 `dataset.batchid`，而 `report.js` 的 `openBatch` 读 `dataset.batchId` → `undefined` → `if (!batchId) return;` 在调用 `redirectTo` **之前**就返回了。无 toast、无红字、fail 回调永不触发 → 完美复现"点了没反应"。
- **定位证据**：全项目 grep，**唯一一处**驼峰 `data-*` 就是 `report.wxml:43`（其余 `dataset.*` 读取点全是全小写键：`id/index/qid/idx/mode/node/type/field`）——与"只有这一处坏、所有条目都点不动"完全吻合；`listByUser` 正常返回（列表数字正确）也排除了数据侧。
- **修复**：
  1. `report.wxml:43`：`data-batchId` → **`data-batch-id`**（连字符转驼峰，正好得到 `dataset.batchId`，JS 读取无需改）；
  2. `report.js` 的 `openBatch`：**回退 `redirectTo` → `navigateTo`**（§53 的"叠栈超 10 层"判断不成立——列表→详情→返回是弹栈不累积；且 `redirectTo` 会替换掉列表页，从详情返回会跳过列表）；保留 `fail` 回调；
  3. `if (!batchId)` 不再静默：加 `log.append('report_openBatch', {batchId, datasetKeys})` + `console.warn` + `wx.showToast`，下次真机测试在「我的 → 运行日志」可直接看到 dataset 内容。
- **教训**：
  ① **WXML 的 `data-*` 属性名一律只用小写 + 连字符**（要驼峰就写 `data-batch-id`，不要写 `data-batchId`）；这是**编译期静默**的坑，不会报错；
  ② **"修改后无效"先回头验证根因，而不是叠加新修复**：本次先入为主认定"页面栈超 10 层"，把改动加在了错误的位置；若一开始就在 `openBatch` 入口打一行 dataset 日志，真机一次就能定位；
  ③ **`if (!x) return;` 这类守卫会让错误彻底静默**——凡是用户可触发的入口守卫，必须留可见反馈/日志；
  ④ **上一次修复未验证就下结论，会污染经验文档**：§53 的错误根因写进了文档，差点二次误导；本次已就地更正。

### 55. 验证 VLM 输出必须有"物理真值"——否则会把幻觉当成功（2026-09-18）
- **现象**：给视觉节点（Qwen-VL，diagnose 的 VISION_PROMPT）加了「红笔批改痕迹」章节后，模型在第 18 题里逐字"转录"出一段**红笔写的必要性证明**，我据此判定"新 prompt 成功"。**用户一眼看出那是假的：该题红笔只有打勾，没写字。**

- **修复/正确做法**：用**像素级红层掩膜**做物理真值 —— 本次实测：全图红色像素仅 **2263 个(0.11%)**、43 个连通域，最大 573px(162×49)/340px(116×95)/217px(15×200)，**没有任何"成段文字"尺度**（成段手写通常宽>300px 且>1500px）→ 红笔确实只有勾叉划线。同法测得第 18 题学生作答区墨迹 **黑/灰 92%、红 0%**（学生用深色笔，此前"学生写红笔"的印象是缩略图渲染误导）。
- **教训**：① **凡"模型说它看到了 X"，都要用可计算的信号交叉验证**（像素统计/连通域/OCR 计数）；② 颜色类判断交给**像素统计**，不要交给 LLM；③ 给模型加"必须转录某类内容"的字段时，要同时给**"没有就写无"的强约束**，否则等于邀请它编；④ 验证样本 ≥3 张，不能单图定论。

### 56. 读图不能拿"看不清"当挡箭牌（2026-09-18）
- **现象**：核对第 19 题手写过程时，我把「由(I)，取 x=(x−y)/xy, y=(y−x)/xy，则有 1/(xy)∈M」这一行**读丢了后半段**，并声称"红笔压着、看不清"。用户指出：**那处很清晰，本来就该读得出来**；而且那正是他自己知道的逻辑错误所在（两个**互为相反数**的量套"加法封闭"，和恒为 0，推不出 1/(xy)）。
- **根因**：① 遇到连笔就**停止努力、声明"读不清"**（廉价免责）；② 只做"转写忠实度"检查，**不做数学/逻辑校验**——就算读到了，也要追问"这一步用了哪条性质（①/②/③/(I)）、结论是否匹配该法则"。
- **纠正做法**：① 说"读不清"前必须穷尽手段：**分区裁剪 → 放大 → 对比度增强 → 红/黑分层**（红色掩膜剥离 + inpaint 去红，本轮实测有效）；② 转写验证**两栏同时报**：忠实度 + **推理链是否成立**；③ 数学校验可规则化：「用了哪条性质 → 结论是否匹配」。
- **产品映射（待落地）**：视觉 prompt **禁止用"看不清"回避可读内容**；低置信区域先**分区放大**再读；判定层加"**性质使用检查**"（今天这类错误正好是"法则与结论不匹配"）。

### 57. 单题裁切图 39/39 全缺——jpeg-js 的 Uint8Array 没有 Buffer.copy，又被静默 catch 吞了（2026-09-18）
- **现象**：线上 `questions` **39/39 全无 `cropFileID`** → `judgeOne` 里"有裁剪图才走"的**单题精读分支从来没执行过**，判定一直吃的是**整页级文本**（噪声最大）。而 08-30 的"切题 v1"功能明明已部署（线上 diagnose 修改时间 08-30 23:22）。
- **根因**：`cloudfunctions/diagnose/imageCrop.js` 的 `decodeNormalized` 用 `jpeg.decode(buf, { useTArray: true })` → 返回的 `data` 是 **Uint8Array**（不是 Node Buffer），**没有 `.copy()` 方法**；`cropBitmap` 里写了 `bmp.data.copy(...)` → **每次调用必抛 TypeError**；而调用处是 `try { ... } catch (e) { console.warn(...) }` → **静默降级成"无裁剪图"**；云函数日志走 CLS，本环境 `topic not exist` 查不到 → 39 次全失败，无人察觉。
- **修复**：`out.data.set(src.subarray(si, si + w * 4), row * w * 4)`（`Buffer.alloc` 出来的目标，用 `set` + `subarray` 兼容 Uint8Array/Buffer）。**本机真图实测**：裁剪出 1026×691 / 123KB JPEG ✅（修复前必抛 `bmp.data.copy is not a function`）。
- **教训**：① **能用"真图跑一遍"验证的，就别只看代码**——这个 bug 本地 20 秒就能复现；② **静默 catch + 不可见日志 = 长时间静默失败**：失败必须落到可查的地方（记录字段/可读日志），不能只 `console.warn`；③ 三方库的返回类型要当场确认（`useTArray` 这类开关会改变类型）。

### 58. 一轮里 6 次小失败：5 次是"凭记忆拼命令/文件名/引号/锚点"，1 次是环境能力缺失（2026-09-18）
- **失败清单**：① 传错文件名（`q19-II-nored-zoom.jpg`，实际 `q19-nored-zoom.jpg`）→ ENOENT；② TS 字符串里嵌英文双引号（`"读不出"`）→ 语法错；③ 自写探针把 `{bmp,orientation,angle}` 整个对象喂给 `cropBitmap` → `ERR_OUT_OF_RANGE`（**但这个错把我引到了真 bug：Uint8Array 没有 Buffer.copy**）；④ `tcb fn log --num 200` —— **已跑过 `--help` 却仍用了不存在的参数**（应为 `--limit`）；⑤ `tcb fn log` 报 `[SearchClsLog] topic not exist`；⑥ 用"文件最后一行"当 edit 锚点，**末行是空行** → `old_string must be a non-empty string`。
- **根因分类**：①②③④⑥ = **凭记忆拼参数/路径/引号/锚点，没做"事实对照"**（与 §56 同一病根，本轮复发两次以上）；⑤ = **环境能力缺失**（本环境 CLS 日志未开通，云函数日志读不到）。
- **新增纪律**：① CLI 参数**从 `--help` 输出里复制**；② 用文件名前先 `ls`；③ TS 字符串里用「」不嵌英文引号；④ edit 锚点取"**最后一行非空内容**"，不取 `lines[length-1]`；⑤ 观测失败**不能依赖云函数日志** → 必须落**记录字段**（这也是决定给裁剪失败加原因字段的原因）。
- **结论**：不换技术路线——这一轮虽小错不断，但**定位并修复了产品级真 bug（单题裁切 39/39 全废）**，"真图跑一遍"的方向是对的，缺的只是操作前的事实核对。
### 59. 裁切“改完却没生效”的第三层根因：拆题循环无条件重建 items，把视觉给的 bbox 全丢了（2026-09-18）
- **现象**：修完 §57 的 jpeg-js 类型错后重跑，`cropError` 仍全线 `no-bbox`，裁切图依旧 0 张——看起来“我的修复没生效”。
- **三层根因（每层都用真实产出物对照，不靠读代码猜）**：
  ① `jpeg.decode(buf, { useTArray: true })` 返回 Uint8Array，没有 `Buffer.copy` → 每次裁切必抛 TypeError，被静默 catch 吞掉（§57）。
  ② 视觉返回里**经常压根没有 bbox** → 补一次 `BBOX_PROMPT` 专用调用（要求输出 `第N题: [x1,y1,x2,y2]`），本机实测输出稳定。
  ③ **真凶**：`diagnose` 第 ② 步循环写成 `let items = await aiSplitQuestions(vr.report)`——**无条件用纯文本重新拆题，把刚带 bbox 的 `vr.items` 整个丢掉**，于是每道题的 bbox 恒为 undefined → 全部 `no-bbox`。
- **修复**：`let items = Array.isArray(vr.items) ? vr.items : []; if (!items.length) items = await aiSplitQuestions(vr.report);`（优先复用带 bbox 的 items，视觉没给时才退回文本拆题）。
- **验证（全量重跑 9 批次，17:51:16→18:03:56，exit=0）**：**28/28 题裁切成功、`cropError` 全为 `null`**；判定 28/28 落库（`processScore` 呈 1/0.6/0.2/0 分布，`knowledgeUsage` 挂图谱节点）；9 个批次报告全部重新生成；报告页每题渲染单题裁切图（`report.wxml:91` 优先 `detail.cropFileID`，整页原图仅兜底并标注）。拆题数量与旧数据一致（旧 29 / 新 28，差异见下方“待确认”），说明复用 items 未导致少拆。
- **教训**：① 修复后必须**看真实产出物**（裁切图文件 + 落库字段），“代码改对了” ≠ “链路生效”；② **中间产物被下游重建**是一类极隐蔽的 bug：修上游产物时要 grep 下游是否**真的在用**它（本次是“算了但没用”）；③ 三层根因会让排查者反复怀疑“修复无效”——**每修一层都必须重跑取新证据**再下结论。

## 五、节点化图引擎 / 云函数部署（2026-09-19，D4）
### 0. 元规则（先看这两条，能挡掉本类一大半错误；2026-09-19 复盘 D4 时 12 次失败的根因归类）

**元规则 1：多行脚本/命令一律先落盘，禁止内联拼字符串**
- **现象**：`run_code` 里把 shell 片段拼成模板字符串 → `${` 撞模板插值、反引号转义打架；数组 `join(' ')` 拼 shell → `{ ... }` 挤成一行报 `syntax error near '}'`；把 JS 压成一行写进字符串 → 括号错位 `Unexpected identifier`；脚本写在 `/tmp` 却用相对 `require('./src/...')` → MODULE_NOT_FOUND。
- **做法**：① 凡是超过一行的脚本，**用 write 工具写到文件再执行**（本轮后半段的 `/tmp/tcb-mgr/*.js`、`/tmp/prodstats/*.cjs` 全部如此，之后 A 类错误归零）；② 必须内联时用数组 `join('\n')`（不是 `join(' ')`），并在每个片段内避免 `${` / 反引号；③ 脚本要用相对路径 require 时，`cd` 到模块目录**或**用绝对路径。

**元规则 2：动环境前先做一次只读探测，禁止凭笔记/记忆假设**
- **现象**：以为函数已部署 → `ResourceNotFound.Function`；以为 creds 里有 `ENV_ID` → `InvalidParameter EnvId is required`；以为 SDK 收对象参数 → `getFunctionDetail({name})` 报参数类型错；以为环境变量是对象 → `Environment.Variables` 其实是 `[{Key,Value}]`，改名调用「成功」但没生效；以为更新代码会保留依赖 → `updateFunctionCode` 把云端 `node_modules` 清掉；`add({data:{...}})` → 字段被塞进 `data`，云函数读 `userId` 为 undefined → 403（**这条已记过一次，属重犯**）。
- **做法**：每个环境动作前先跑一条**只读**探测——列函数 / 查配置键名 / `grep` 对应 SDK 的实现（`grep -n 'async xxx' -A 30 lib/...`）/ `grep` 自己以前跑通的脚本（`/tmp/prodstats/*.cjs`）确认契约。探测成本几秒，猜错成本一轮。

**元规则 3：失败先打真实错误，再谈修复**
- **现象**：`judgeQuestion` 只回 `code=500 判定失败，请重试`，看不出任何原因；加上 `console.error(e.stack)` 后一次就定位到 `crypto is not defined`（且耗时 12ms 说明根本没走到业务逻辑）。
- **做法**：捕获处**必须留真实 message/stack**（`debug` 开关或日志都行）；「秒级失败」优先怀疑加载/初始化/环境，而不是业务。

### 1. Node 18 云函数里跑 LangGraph → `crypto is not defined`
- **现象**：`graphEngine` 的 `judgeQuestion` 一调用就 `code=500 判定失败，请重试｜crypto is not defined`，耗时仅 12~34ms（说明还没走到 AI 调用）。日志栈指向 `@langchain/langgraph-checkpoint/dist/base.cjs:15 emptyCheckpoint`。
- **根因**：`@langchain/langgraph-checkpoint` 直接用**全局 Web Crypto** 的 `crypto.randomUUID()`；全局 `crypto` 从 **Node 19** 才有，云函数 runtime 是 `Nodejs18.15` → 全局没有。（本机 Node 24 有 → 本地跑永远不复现。）
- **修复**：`index.js` 顶部、**早于 require 图**：`if (!globalThis.crypto) globalThis.crypto = require('node:crypto').webcrypto;`
- **教训**：① 本地能跑 ≠ 云端能跑，**runtime 差异要当作一类根因**（Node 18/20 的全局 API 差异）；② 「秒级失败 + 无业务日志」几乎一定是加载/初始化阶段的问题，先把真实错误打出来（`console.error(e.stack)`）再谈修复——本次第一轮只回了 `500 判定失败`，白跑一轮。

### 2. `updateFunctionCode` 会把云端 node_modules 清掉且不重装
- **现象**：用 `@cloudbase/manager-node` 的 `functions.updateFunctionCode({func:{name}, base64Code})` 更新代码后，函数一调用就 `Cannot find module 'wx-server-sdk'`（创建时 `installDependency: true` 装好的依赖没了）。
- **根因**：`UpdateFunctionCode` 是**整包替换**，不会重跑依赖安装。
- **修复**：代码更新改用 `.github/ci/upload-functions.cjs`（miniprogram-ci `cloud.uploadFunction` + `remoteNpmInstall: true`），云端会「installing dependencies in the cloud and deploying」。
- **教训**：**创建**函数和**更新**函数是两条不同语义的通道——create 能装依赖，update 不能。已建函数后续更新一律走 CI 脚本。

### 3. manager-node 的接口是位置参数、环境变量是数组（不是对象）
- **现象**：`getFunctionDetail({ name: 'judgeOne' })` 报 `The value type of parameter FunctionName is not valid`；`updateFunctionConfig({ ..., environment: { variables: {K:V} } })` 返回成功但环境变量没设上；`Environment.Variables` 读出来是 `{0:…,1:…}`。
- **根因**：① 该 SDK 里 `getFunctionDetail(name, codeSecret)` / `invokeFunction(name, params)` / `deleteFunction(name)` 都是**位置参数**；② `Environment.Variables` 是 **`[{Key,Value}]` 数组**；③ `updateFunctionConfig` 的白名单里**根本没有环境变量**（只能在 createFunction 时通过 `func.envVariables` 设置）。
- **修复**：环境变量改为在**创建时**传 `func.envVariables`（删掉重建）；更新超时/内存才用 `updateFunctionConfig({name, timeout, memorySize})`。
- **教训**：管理类 SDK 与运行期 SDK 的契约不同，动手前先 `grep` 一下 `lib/function/index.js` 的函数签名，比猜快得多。

### 4. FunctionPacker.getBase64Code() 报 ENOENT（zip 没生成）
- **现象**：`new FunctionPacker({...}).build()` 后 `getBase64Code()` 抛 `ENOENT .../.cloudbase_temp_<name>/<name>.zip`。
- **修复**：不用 FunctionPacker，改**手动打 zip**：把函数目录（排除 `node_modules`/`.npmcache`/`test`）暂存到 `/tmp/ge-stage/<name>/`，`cd` 进去 `zip -qr ../<name>.zip .`（**条目必须在根**，不能套一层目录，否则 `index.main` 找不到），再读 zip → base64 → `createFunction`。
- **教训**：官方打包器出问题时，**自己打 zip 更可控**；关键约束是「zip 根目录 = 函数根目录」。

### 5. 云函数代码目录里的 `.npmcache` 会把包体撑到 39MB
- **现象**：`graphEngine` 目录打成 39150KB、被判定「超限」。
- **根因**：本地 `npm i --cache /tmp/npm-cache` 之外，目录里还残留 `.npmcache/`（几万个小文件），`ignore: ['node_modules/**']` 管不到它。
- **修复**：暂存/打包时同时排除 `node_modules` + `.npmcache` + `test` → **43KB**。
- **教训**：打包前先看**目录里有什么**（`du -sh *`），别只看 `.gitignore`。

### 6. 拿真实题目做「全图」验证 = 污染学生档案
- **现象（设计层面）**：D4 全图会写 `questions` / `knowledge_progress` / `mastery_logs`，直接用线上真题跑，等于把学生的掌握度重算一遍。
- **修复**：**临时用户 + 临时题**：造 `userId='d4-shadow-test'` 的临时批次与临时题（内容照抄真题、`cropFileID` 只读复用）→ 跑全图 → 核对写库 → `finally` 清理（含 `mastery_logs` / `knowledge_progress` / `custom_nodes`）。实测跑完各集合残留 0。
- **教训**：验证要**先设计退出路径**（能删干净才敢写）；只读影子用 `until` 截断到 N3，一个库都不写。

### 7. 重犯：node-sdk 的 `add({ data: {...} })` 会把字段塞进 `data` 字段
- **现象**：脚本用 `db.collection('questions').add({ data: { userId: 'd4-shadow-test', ... } })` 造临时题，云函数读出来 `userId` 是 `undefined` → 判定直接 `403 无权操作他人题目`。
- **修复**：本环境 `@cloudbase/node-sdk` 用 `add({ userId, batchId, ... })`（**不加 `data` 包装**）。
- **教训**：第 11 条记忆里已记过一次，**同类错误第二次踩**——写脚本前先 `grep` 自己以前跑通的脚本（`/tmp/prodstats/*.cjs`）确认契约。

### 8. LangGraph：截断拓扑时「不可达节点」会让 compile 直接失败
- **现象**：想加 `until`（只跑到 N3，用于只读影子对比）→ `createJudgeGraph(deps, { until: 'N3_normalize' })` 抛 ``Node `N4_persistQuestion` is not reachable``。
- **根因**：LangGraph 编译期校验可达性，**注册了就必须连上**。
- **修复**：截断时**只注册用到的节点**——把节点定义写成 `[name, factory]` 列表，按 `until` 切片后再 `addNode` + 连边。
- **教训**：图的「裁剪」要在**建图前**做，不是建完再删边。

### 9. 用程序拼 markdown 时，模板字符串里的反引号没转义 → 整段代码解析失败（2026-09-19）
- **现象**：往 `doc/decision-log.md` 追加决策 046 的程序报 `Unexpected character '）'`，看着像环境/依赖问题。
- **根因**：用模板字符串（反引号）包整段 markdown，正文里又出现了**未转义的反引号**（`judgeOne`、`deriveOnly` 那几处）→ 模板字面量提前结束，后面的中文标点被当成代码解析。
- **修复**：改成**单引号（或双引号）字符串数组，再用换行符 join**——反引号在引号串里无特殊含义；中文正文本来也不含引号冲突。
- **另一坑**：改文件前**必须先 read 一次**（`tail`/`cat` 不算数），否则被 fs 策略拒：`file has not been read`。
- **教训**：报错字符是**中文标点/怪字符**时，先怀疑**自己拼字符串的引号嵌套**，别先怀疑环境；两次失败后先想「两次失败的共同点」而不是换第三种写法。

### 10. 「照抄线上」抄漏了顺序：新引擎 deriveAll 直接用 raw 过程字段（2026-09-19，D5 对拍发现）
- **现象**：同一份模型 raw 下，新壳 `graphEngine/lib/normalize.deriveAll` 与线上 `judgeOne` 的整理段有 3 处不一致——选填题（选择/填空）只要模型给了 `processAvailable:true` 或非空 `segments` 就会判「过程风险」（线上禁止）；填空题无作答但有模型分段时漏判空白（`errorAttribution` 该是「整题空白未下笔」却是 null）。
- **根因**：线上顺序是「**先**按题型把选填题的过程字段归一为空（`segOut/bpOut/paOut`）→ **再**用它推导空白与 errorType」；新壳把判据/阈值逐行照抄了，**但推导时直接读 raw 的 `segments/breakpoint/processAvailable`**。照抄了表达式，没照抄顺序。
- **修复**：`deriveAll` 内部先 `normalizeProcessFields` 再推导 → 同 raw 对拍 0 差异；补 2 条回归测试（`npm test` 47/47）。
- **教训**：① **照抄行为 ≠ 照抄表达式**——「谁先谁后」也是行为的一部分；② 单测要专门构造**输入自相矛盾**的夹具（选填题却带 `processAvailable:true`），正常夹具永远测不出顺序错；③ 把「线上那段」抽成可在本机 require 的纯模块后，这类问题几分钟就能查到，**不用花一分钱 AI 调用**——这是 D5 影子对比能便宜跑起来的前提。
### 11. 多步改同一个文件：别用行号当锚点，也别手打多行 old_string（2026-09-19，D5 重构踩坑）
- **现象**：同一次程序里对 `judgeOne/index.js` 做 5 处改动，前 3 处（含删掉上面 6 行 LR 表）成功，第 4 处报「clampParams 定位失败」——因为我按**旧行号** `read(225)` 取要删的函数，而上面刚删了 6 行，行号已经整体上移。文件一度停在「半重构」状态（LR 已删、函数还在、require 未加）。
- **根因**：把**行号**当成了稳定地址。行号只在「文件未被改动」时有效；同一程序里前面的 edit 会改变后面的行号。
- **修复（已验证有效，改完 0 失败）**：
  1. **定位用文本**：先 `grep -n '<函数签名>'` 拿行号，再 `read` 该处，并**断言首行/末行**符合预期；不符就停。
  2. **old_string 从 read 的结果里生成**，绝不手打多行：`const old = read(...).lines.map(l => l.text).join('\n')` —— 零转写风险。
### 12. 说「本机没有凭据」之前，检索面要铺全（2026-09-25，D5 真数据轮）
- **现象**：我断言「本机没有 CloudBase 凭据，必须重新授权」，用户反问「我记得我不是发给你了好多次 secretkey 吗」——查下去发现密钥**一直都在**：`~/.zsh_history` 里成对躺着 `export TENCENT_SECRET_ID=AKID…`（36 位）+ `export TENCENT_SECRET_KEY=…`（32 位），另有一份在 DSH 的旧会话记录里。
- **根因**：我只查了 4 个地方（环境变量、`~/.config/cloudbase`、`~/.cloudbase`、`~/.tcb`），**漏了 shell 历史与 AI 会话存储**——而这两处恰恰是「用户手工粘贴过密钥」最可能留下的地方。
- **正确检索面（按顺序）**：① `env | grep -i -E 'tcb|tencent|secret'` ② `~/.config/cloudbase`、`~/.cloudbase`、`~/.tcb` ③ **`~/.zsh_history` / `~/.bash_history`**（`grep -c AKID`；用掩码打印，别把值打到屏上）④ **DSH 会话存储** `~/.dsh/storages/session_*/sessions/*.json` ⑤ 工作区/桌面里名字像密钥的文件。
- **本项目的凭据事实**：腾讯云 API 密钥对在 `~/.zsh_history`；非交互登录 `tcb login --apiKeyId <SecretID> --apiKey <SecretKey>`（`-k` 为交互输入、不进历史）；云环境 `cloud1-d8g0ty39wd73f430a`；登录态落在 `~/.config/cloudbase`。**仓库里没有真密钥**（`scripts/poc/question-split-poc.js` 用 `process.env.TCB_SECRET_ID`，CI 文档只写 Secret 名，`scripts/zhixue/` 已 gitignore）→ 无泄露。
- **查库**：`tcb db nosql execute --json -e <env> --command '[{"TableName":"questions","CommandType":"QUERY","Command":"{\"find\":\"questions\",\"filter\":{},\"limit\":100}"}]'`；返回是 **Mongo 扩展 JSON**（`{"$numberInt":"1"}` / `{"$numberDouble":"0.1"}`），取数后必须递归 unwrap，否则 D/P 会变成对象。
- **教训**：① 「没有 X」这类断言，先问「我查了哪几个地方」——**检索面不足得出的否定结论，比猜还危险**（它让人放弃继续找）；② 用 `execFileSync(cmd, [args])` 传参数数组，绕开 shell 引号地狱（本次一次成功，对比前面 `node -e` 的翻车）；③ 打印密钥一律掩码（前 4 + 后 4 + 长度）。
  3. **要按行号改多处时，从大行号往小行号改**（下面的改动不影响上面的行号）；否则每改一处重新定位。
  4. **读文件只用 read 工具**：`cat`/`tail`/`sed` 看过不算「读过」，随后 edit 会被 fs 策略拒（`file has not been read`）。
  5. **一步一验**：每个 edit 后立刻最小断言（`node --check` / grep 残留 / 断言 edit 成功），失败即停，**不要带着半成品状态继续下一步**。
- **教训**：和 §五-9 是同一个病根——**手工拼文本 + 手工推算地址**。凡是能从工具返回值里「取」的字符串，就不要手写；凡是能靠内容定位的，就不要靠行号。同一类错误在一个 turn 里出现 3 次以上，说明该换做法，而不是换参数。
