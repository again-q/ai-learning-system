## 1. 页面清单

| 页面 | 路径 | tabBar | 功能 |
|------|------|--------|------|
| 拍照页 | pages/photo/photo | 否（从首页 / 报告页空态进入） | 拍照/选图、预览删除、提交分析 |

## 2. 页面交互规则

- **入口**：首页「开始诊断」按钮（`goPhoto`）或报告页空态「去诊断」按钮（`goDiagnose`）→ `wx.navigateTo` 拍照页
- **拍照**：选择拍摄或从相册选图，最多 9 张（count 参数）
- **预览**：照片网格展示，点击缩略图预览大图；点 × 移除单张
- **提交**：点「完成，开始分析」→ 逐张 `wx.cloud.uploadFile` → 调 `photoUpload`（登记批次，拿 `batchId`）→ 调 `diagnose` → **跳转复核页**（`/packageDiagnose/pages/review/review?batchId=`）
- **进度**：提交后显示全屏遮罩（条件 `analyzing || submitting`）——「上传中…」→「AI 识别题目中…」，含进度条与预计耗时
- **离开后继续跑（重要）**：离开拍照页**或整个小程序**后，上传/诊断链路**不中止，继续跑完**。离开页面（小程序仍在前台）逻辑层继续执行，必然能跑完；切到后台（app hide）时微信会限制云能力，按 §7「诊断结果过期抢救」处理。
- **边界**：未选照片时「完成」不可点；超 9 张提示「最多 9 张照片」；照片质量过低会在缩略图标 ❌ 并在提交时弹窗拦截（可「移除并继续」或「取消」）

## 3. API 调用映射

小程序侧统一走 `wx.cloud.callFunction`（非 HTTP）：

| 功能 | 云函数 | 请求 | 响应关键字段 |
|------|--------|------|------------|
| 登记批次 | photoUpload | `{fileIds}` | `code`, `data.batchId` |
| 触发诊断 | diagnose | `{batchId}`（`timeout: 120000`） | `code`, `data.totalQuestions`, `data.failedCount`, `data.questions[]` |
| 抢救 / 复核取题 | judgeOne | `{action: 'listQuestions', batchId}` | `code`, `data[]`（题目数组，长度用作抢救完成判据） |

## 4. 状态与存储

- **globalData**：无页面级持久状态（登录态读 `app.globalData.userInfo`）
- **页面 data**：`{images, submitting, analyzing, progressText, estimatedText, totalQuestions, doneCount, progressPercent, pipelineError}`
  - `images` 元素形如 `{path, qualityOk, qualityIssues}`（注意 `path` 是临时文件路径，**不是字符串数组**）
- **页面参数**：**不接收任何参数**（`onLoad()` 为空）；批次在提交成功后通过跳转传给复核页
- **链路日志**：写本地 storage key `upload_logs`（`utils/upload-log`，最多 200 条）；拍照页长按标题「拍照诊断」可复制

## 5. 微信能力使用

| 能力 | 目的 |
|------|------|
| `wx.chooseMedia` | 拍照 / 相册选图（camera + album） |
| `wx.getImageInfo` + `wx.compressImage` | 长边 ≤2000px 压缩（失败回退原图，不阻塞上传） |
| `wx.cloud.uploadFile` | **直传云存储**（路径 `photos/{openid}/…`）；`photoUpload` 只登记批次，不重复上传 |
| `utils/upload-log` | 链路日志（storage `upload_logs`），排查耗时/失败用 |

## 6. 生命周期钩子

| 钩子 | 动作 |
|------|------|
| onLoad | 空实现（本页不接收参数） |
| onHide | 链路日志留痕 `photo_hide`（含 `submitting`/`analyzing`） |
| onUnload | 链路日志留痕 `photo_unload`（含 `submitting`/`analyzing`） |

> ⚠️ **`onHide`/`onUnload` 只留痕，绝不中止上传/诊断链路。** 用户明确要求「离开也继续跑」——离开页面时逻辑层仍在执行，链路本就能跑完；在此处中止反而是破坏行为。

## 7. 错误处理

统一原则：**报错文案面向学生，不面向开发者**——不把云能力原始英文错误（`uploadFile:fail interrupted`、`-404010 result expired` 等）展示给用户。原始错误仍由 `log.append('submit_fail', {error})` 写入链路日志备查。

| 场景 | 处理 |
|------|------|
| 选图超 9 张 | Toast「最多 9 张照片」 |
| 上传/提交失败（通用） | **页内提示**（`.pipeline-error`）+「知道了」「重试」两个按钮；**保留图片列表不重置** |
| 照片上传被中断（`uploadFile:fail`） | 页内提示「照片上传被中断了（可能小程序切到了后台）。照片还在，请保持小程序在前台，再点「重试」。」**无法自动恢复**——上传本身未完成 |
| 诊断结果过期 / 超时（`-404010 result expired` / `-501002 ESOCKETTIMEDOUT`） | **先抢救**：轮询 `judgeOne action:listQuestions`（5s 一次，最长 3 分钟）→ 有 `pending` 题目则**直接跳复核页**；题目都入库但无 `pending`（全部识别失败）则提示「未识别到题目，请换清晰照片后重试」；完全没抢救到才页内提示「分析结果过期了…请点「重试」」或「分析超时了…请点「重试」」 |
| 其他未知错误 | 页内提示「提交失败，请重试。」 |

> **为什么用页内提示而非 Toast**：进度遮罩与系统 Toast 会叠层（先行决策 `b1da109`）。
> **为什么诊断失败要抢救**：`diagnose` 的结果有 TTL，切后台久了客户端取不回（`-404010`），但**云函数在服务端已跑完并把题目写进了 `questions` 集合**——抢救即可免去用户白等一场重来。
> **抢救完成判据（两重）**：① `diagnose` 是「先逐题 `questions.add`、最后才 `batches.update({totalQuestions})`」，只看"题目非空"会拿到**写了一半的残缺题目**，必须**连续两次轮询到相同的 `总数:待判定数` 组成**才算收完；② 是否可进复核页只看 **`status === 'pending'` 的题目数**，与正常路径的 `pendingQ` 同口径——识别失败的题也会入库（`status: 'failed'`），只看题目总数会把"全部识别失败"误判成可进复核页。
> **约束**：`diagnose` 有 `status !== 'pending' → 40003「批次已诊断，请勿重复提交」` 的防重入，因此**恢复只能靠轮询，不能靠重调 diagnose**。

## 10. 测试要点

| 场景 | 预期 |
|------|------|
| 选 4 张照片提交 | 跳转**复核页**（携带 batchId） |
| 不选照片点完成 | 按钮不可点 |
| 选 10 张 | Toast「最多 9 张照片」 |
| 提交中离开页面（点 tab / 返回）再回来 | 链路**继续跑完**，正常进复核页 |
| 提交中把小程序切后台、稍后返回 | 未超 TTL → 正常完成；已超 TTL → **自动抢救**后进复核页；抢救失败才显示人话提示 +「重试」 |
| 诊断失败后点「重试」 | 重新走上传 + 诊断，**照片列表不被清空** |
| 提交中删除照片 | 删除按钮在提交中无效（`submitting` 守卫） |
