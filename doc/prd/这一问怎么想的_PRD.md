## 第 1 节：执行摘要

**一句话定义**：在报告页的每个小问下面放一个很小的入口「这一问怎么想的」；**默认不生成任何内容、不产生任何成本**；学生点了，才当场让 AI 独立做这一问、验证通过后，把**这一问是怎么一步步想到的**讲出来，并标注每一步用到的数学思维；学生可以继续追问；追问若暴露**之前那段诊断文字说错了**，允许当场把那段诊断改掉（判定字段不动）。

**核心业务价值**：

1. **补上「考场为什么做不出来」这个盲区**。扣分点学生自己看得到（分数在那），但「我当时为什么卡住」在考场上自己是看不见的。现有报告只审「哪里没写对」，不解释「这题该怎么想」。
2. **成本可控且按需**。用户明确：「大多题只要复盘错误就可以了」。默认零成本，只为真正想弄懂的那一问付费。
3. **可反驳**（决策 047）。学生能追问；若追问暴露出**之前那段诊断文字说错了**（如把「算错了」说成「省了一步」），AI 当场把那段诊断改掉——这是当前报告最缺的能力。

> ⚠️ **改的是「诊断文案」，不是「判定」**。判定（`errorType` / `processScore` / `errorLevel` / `segments`）一律不动，这守住了决策 061 红线 3「判断权在代码」。

**预期成功指标**：

| 指标 | 目标 |
|---|---|
| 入口点击率 | 解答题（含做对/做错）任一小问被点开（当前 0，因为不存在）；分「错的小问」与「做对的小问」两个口径统计 |
| 追问率 | 点开的学生中，≥30% 会追问至少 1 次 |
| 思路可读性 | 单问思路步数 **prompt 引导 3~6 步**，代码校验放宽到 **2~8 步**（实测按小问拆分后为 3~5 步；极简小问可为 2 步） |
| 成本 | 未点击的题：0 次模型调用；单问生成 ≤3 次调用 |
| 诊断更正 | 追问后更正的诊断文案，必须写明「原来说了什么、为什么不对、改成什么」 |

## 第 2 节：项目背景与目标

### 2.1 背景描述

报告页当前的四段结构（这次的情况 / 错在哪 / 接下来做什么 / 你的记录），在「错在哪」这一段里对解答题只做**过程审阅**：给出题目、学生写的、标准做法，标出断点。

实测（2026-10-18，第 19 题）暴露出三层问题：

1. **错因停留在「哪里断了」，没说「为什么这么想会断」**。第 19 题学生真实错误是「把 (y−x)/xy + (x−y)/xy 算成 1/(xy)」，但因为 1/(xy) 取倒数正好是 xy，**结论形态正确**，学生自己有理由相信证完了。这类错，扣分点告诉不了他。
2. **标准做法本身可能是「一种走法」**。同一道第 19 题，三次独立求解跑出三种不同的正确证法（平方引理 / 加两次除二 / 平方差减二）。所以不能写「标准做法」，只能写「一种走法」。
3. **学生要的不是通法**。用户原话：「我不想教学生一种通法，而是告诉学生这个地方是怎么一步步自然想到的。」

而 2026-10-18 的实测已确认：模型**能**产出这种形态。按小问生成时，每问 3~5 步，每步讲清「手上有什么 / 还缺什么 / 为什么走这步 / 具体做了什么」，并能标注数学思维（如「转化策略」「倒推法 + 构造法」）。

### 2.2 业务目标

| 目标 | 说明 |
|---|---|
| G1 | 每个小问各有独立入口，默认不生成、零成本 |
| G2 | 点开才生成：AI 独立求解该小问 → 验证 → 通过才出思路 |
| G3 | 思路按「一步一动机」呈现，每步标数学思维（名字取自 54 项，只留名字） |
| G4 | 学生可继续追问，追问当场作答 |
| G5 | 追问暴露**原诊断文案**有误时，允许更正那段诊断（comment / inference / hook），但必须写清「原来错在哪」，并留痕、学生确认 |

### 2.3 成功指标

见第 1 节表格。补充可观测项：

- **验证拦截率**：给验证器喂故意写错的解答，必须拦下（当前未验证）
- **诊断更正可追溯率**：每次更正都有 `revisions` 记录（改了什么、依据、谁确认）
- **判定零改动**：诊断更正**不得**修改 `errorType` / `processScore` / `errorLevel` / `segments`（可自动校验）

### 2.4 项目范围

**做（本期）**：

| # | 内容 |
|---|---|
| S1 | 报告页：解答题按小问切分，每小问下加入口 |
| S2 | 后端：单小问「求解 → 验证 → 出思路」接口 |
| S3 | 后端：追问接口（多轮对话，有轮数上限） |
| S4 | 后端：**诊断文案更正**（改 comment / inference / hook，不动判定；带依据 + 学生确认 + 留痕） |
| S5 | 54 项思维清单入库，供 prompt 引用 |
| S6 | ✅ 验证器可信度验证（**已完成 2026-10-18**，5/5 错解全部拦下） |

**不做（本期明确排除）**：

| # | 不做 | 理由 |
|---|---|---|
| N1 | 一次给多种解法 | 用户：「目前，AI 教练能做出来的话，就先给一个方法的思路」；多种解法留到 AI 教练成熟后 |
| N2 | 通法 / 套路教学 | 用户明确拒绝 |
| N3-改 | 所有小问都给入口（含做对的） | 用户拍板：「给入口但都是按需」——不点就不花钱，做对的题想学思路也能点 |
| N4 | 把整道题一次性生成 | 已改为按小问，整题生成太贵且混在一起 |
| N5 | 思路讲解替换现有过程审阅 | 两者并存，过程审阅不变 |
| N6 | **改判定**（errorType / P / errorLevel / segments） | 判定是客观事实，归代码裁决（决策 061 红线 3）；追问只改 AI 自己写的诊断文案 |

## 第 3 节：用户角色与场景

### 3.1 用户画像

高一学生，数学中上水平。丢分集中在解答题的步骤分，不是「不会做」而是「做的时候自己发现不了问题」。

### 3.2 使用场景

**场景 A：只想知道自己错在哪（默认，最常见）**

学生打开报告 → 看到第 19 题第(3)问标红 → 看完错因，够了 → 不点入口 → **零成本**。

（做对的 (1)(2) 也有入口，但同样不点不生成——学生想学那道题的思路时随时可点。）

**场景 B：这问我不服 / 想弄懂怎么做**

学生点第(3)问的「这一问怎么想的」→ 显示「AI 正在想…」→ 3~6 步思路出现，每步有手上/还缺/为什么/做法 + 数学思维 → 学生读懂了。

**场景 C：看了还是不懂，追问**

学生问「这步为什么要先证平方？」→ AI 当场答 → 学生继续问 → 最多 N 轮。

**场景 D：学生发现 AI 的诊断说错了**

学生问「你说我『缺了中间环节』，但我其实是算错了，不是省步骤吧？」→ AI 复核自己的诊断 → 承认那段诊断说错了 → 弹出更正卡片（原来怎么说 → 改成什么 + 为什么）→ 学生点「按这次更正」→ 落库并留痕。

> 注意：这里更正的是 `diagnosis.inference` 这段**文案**，不是 `errorType` 这个判定。判定（是「结果错」还是「过程风险」）由代码按证据决定，AI 无权改。

### 3.3 用户旅程

```
报告页（错在哪）
  └ 第19题
      ├ (1) 做对了        → [这一问怎么想的 ›]（同样有入口，不点不花钱）
      ├ (2) 做对了        → [这一问怎么想的 ›]
      └ (3) ✗ 乘法不成立
            ├ 你写的（原文分段）
            ├ 正确做法 · 一种走法
            └ [这一问怎么想的 ›]   ← 点
                  ↓
            ① 独立求解（不看学生过程，避免被带偏）
                  ↓
            ② 逐步验证 —— 不通过就诚实说「这题我也没做稳」
                  ↓
            ③ 输出 3~6 步思路 + 数学思维标注
                  ↓
            [追问输入框]  ← 可继续
                  ↓
            若暴露原诊断有误 → 更正卡片（改的是什么文案 + 为什么）→ 学生确认 → 落库
                                 （判定字段不动）
```

## 第 4 节：功能需求

### 4.1 业务流程

```
学生点击「这一问怎么想的」
        ↓
前端：调用 thinking 接口（questionId + subQuestionNo）
        ↓
后端：读取该题 + 该小问的学生作答
        ↓
① 独立求解：只针对该小问，开思考，不看学生过程
        ↓
② 逐步验证：每一步是否严格成立
        ↓
不通过 → 返回 verified=false，前端显示「这一问 AI 没能稳稳做出来」，不以 AI 结论为准
        ↓
通过 → ③ 生成思路：3~6 步，每步 have/lack/why/do + thinking{cards, say}
        ↓
返回前端渲染
        ↓
学生追问 → 多轮对话（带上下文）→ 每轮计入上限
        ↓
若 AI 判断原判定可能有误 → 返回 correction 建议（含验算证据）
        ↓
学生点「按这次更正」→ 落库 + 写 revisions
```

### 4.2 功能列表

| ID | 功能 | 优先级 | 说明 |
|---|---|---|---|
| F-001 | 小问切分 | P0 | 把一道解答题的作答与参考过程按 (1)(2)(3) 切开；切不出来则整题作为一问处理 |
| F-002 | 小问入口 | P0 | **每个小问**（含做对的）下都加一行入口；默认不生成，点击才触发 |
| F-003 | 按需生成 | P0 | 点击才调用，默认零成本 |
| F-004 | 独立求解 | P0 | 只解该小问，开思考 |
| F-005 | 逐步验证 | P0 | 验证不通过不出思路 |
| F-006 | 思路生成 | P0 | 3~6 步，每步四要素 + 数学思维 |
| F-007 | 数学思维标注 | P0 | 名字取自 54 项清单，只输出名字，不自造 |
| F-008 | 追问 | P0 | 多轮，有上限 |
| F-009 | 诊断文案更正 | P1 | 只改 diagnosis 的 comment/inference/hook；写清原话错在哪；学生确认；留痕。**不碰判定字段** |
| F-010 | 思路缓存 | P1 | 同一小问生成过则复用（见 8.1 假设 H3） |

### 4.3 权限逻辑

- 只有题目所属用户（`userId` / `_openid`）能触发与追问
- 诊断更正必须经学生显式确认，AI 不能自行落库
- 诊断更正**不允许**修改 `errorType` / `processScore` / `errorLevel` / `segments` / `breakpoint`（后端必须校验白名单）

### 4.4 验收标准

| ID | 标准 | 验证方式 |
|---|---|---|
| AC-1 | 默认状态下，报告页不产生任何「思路」相关模型调用 | 日志核验 |
| AC-2 | 每小问思路步数落在 3~6 步 | 抽样 10 次统计 |
| AC-3 | 数学思维输出**不含**花色/牌号（如 `♠10`），只有名字 | 正则校验 `[♠♥♦♣]` |
| AC-4 | 验证不通过时，不返回思路（返回 verified=false） | 构造错误解答测试 |
| AC-5 | 给验证器喂**故意写错**的解答，必须判「不成立」 | ✅ 已通过：5 份错解 5/5 拦下（`output/probe-verifier-redteam.json`）；新增错解回归时重跑 |
| AC-6 | 诊断更正必须带 `evidence`（原话错在哪），且学生确认前不落库 | 代码审查 + 用例 |
| AC-8 | 诊断更正**只允许**改 `diagnosis.comment/inference/hook` 三个字段；试图改判定字段必须被后端拒绝 | 单测：提交 errorType 修改应返回失败 |
| AC-7 | 追问达到上限后，明确提示且不再消耗调用 | 用例 |

## 第 5 节：业务规则与数据规范

### 5.1 核心业务规则

| 规则 | 内容 |
|---|---|
| R1 | **判断权在代码**（决策 061 红线 3）：是否「验证通过」由代码按返回字段判定，不由模型自述 |
| R2 | **验证不通过必须诚实降级**：说「这一问我没稳稳做出来」，不给思路 |
| R3 | **只给「一种走法」**，文案禁止出现「标准做法」「标准答案」 |
| R4 | **数学思维只输出名字**，来自 54 项清单；简单步骤允许留空并写「直接套用条件」 |
| R5 | **禁止通法/套路**：文案不得出现「这类题一般」「套路」「技巧」 |
| R6 | **诊断更正必须可反驳留痕**：写 `revisions`，含字段名/原话/新话/依据/时间 |
| R8 | **判定字段只读**：`errorType` / `processScore` / `errorLevel` / `segments` / `breakpoint` 在追问链路中**一律不可写**，后端白名单校验 |
| R7 | **所有小问都给入口，但一律按需**：不点不生成、不花钱（N3-改） |

### 5.2 业务数据规范

**思路记录（建议存 `questions.subThinking[]` 或独立集合）**：

```json
{
  "questionId": "...",
  "subNo": "(3)",
  "verified": true,
  "verifiedAt": "2026-10-18T...",
  "solution": { "answer": "...", "steps": [...] },
  "thinking": {
    "goal": "...",
    "steps": [{
      "n": 1,
      "have": "...", "lack": "...", "why": "...", "do": "...",
      "thinking": { "cards": ["转化策略"], "say": "..." }
    }],
    "ending": "..."
  },
  "model": "deepseek-v4-flash",
  "costMs": 60000
}
```

**诊断文案更正（写入 `questions.revisions[]`，该字段已存在）**：

```json
{
  "field": "diagnosis.inference",
  "before": "乘法封闭性写到「由③取 x=1/(1/xy)」就停住了，没走完。",
  "after": "这一步不是「没写完」，而是两个分式相加算错了：(y−x)/xy + (x−y)/xy = 0，不是 1/(xy)。",
  "evidence": "原诊断说「停住了/没走完」，但学生原文这里有「证毕」，说明他不是没写完，是算错了还以为是证的。",
  "confirmedBy": "student",
  "createdAt": "..."
}
```

**⚠️ 白名单（后端必须校验）**：

| 可改 | 不可改（只读） |
|---|---|
| `diagnosis.comment` | `errorType` |
| `diagnosis.inference` | `processScore` |
| `diagnosis.hook` | `errorLevel` |
| | `segments` / `breakpoint` |
| | `officialScore` / `officialStatus` |

### 5.3 业务流程约束

- 单小问生成 **正常路径 3 次**模型调用（求解 / 验证 / 思路）；
  **异常重试路径最多 6 次**（验证失败时重解，最多重试 2 次，见详细设计 §3.4.3）
- 追问**不设轮数上限**（用户 2026-10-18 拍板：「不认可，一次」——指追问一次到底，不截断）
  - ⚠️ 代价：长对话成本无上限，靠「单次会话超时」与「用户主动结束」控制，不做硬性截断
- 生成超时上限建议 90s（实测单问约 40~60s）

## 第 8 节：假设与风险 ⭐

### 8.1 假设条件

| ID | 假设 | 若不成立的影响 |
|---|---|---|
| H1 | 「重量档」（AI 独立求解 + 验证）能力可用 | 整个方案的地基；决策 061 标注「执行器未写」，需新建 |
| H2 | 能按小问切开学生作答 | 切不开就只能整题生成（贵且混） |
| H3 | 思路可以缓存复用 | 每次重算成本高，且同一问可能给出不同走法（实测三种） |
| H4 | 验证器能拦下错误解答 | **未验证**。若拦不住，「验证通过才给思路」形同虚设 |

### 8.2 风险清单
