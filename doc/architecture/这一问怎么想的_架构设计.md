# 「这一问怎么想的」· 架构设计

> 状态：**设计初稿**（2026-10-18）
> 上游：`doc/prd/这一问怎么想的_PRD.md`（PRD-20261018-001）
> 关联决策：061（分档诊断）、047（可核验/可执行/可反驳）、059（解答题过程审阅）
> 本文回答：**这套东西放在哪儿、谁调谁、数据怎么走、边界在哪**

---

## 0. 大白话：这东西是个什么

打个比方。

现在的报告页像一张**批改过的卷子**：告诉你哪一步被划了红叉，旁边贴着老师给的"正确写法"。

但学生真正卡住的那一刻是——**他做的时候，根本没意识到自己走错了路**。第 19 题就是：他算出 `1/(xy)`，取倒数正好是 `xy`，看起来证完了。**结论形态对了，所以他有理由相信自己**。

这套东西是在卷子旁边加一个**随叫随到的老师**：

```
学生：「这一问怎么想的？」
   ↓
老师不当场编 —— 先自己闷头做一遍（不看学生答案，免得被带偏）
   ↓
做完再自己检查一遍（查每一步是不是真的成立）
   ↓
检查通过了，才开口讲：这题是一步步怎么想到的
   ↓
学生还能追问，老师说错了也能改口
```

**三个关键设计**：

| 设计 | 为什么 |
|---|---|
| **不点不生成** | 多数题学生只要复盘错误。默认零成本，想学才点 |
| **先自己做完再讲** | 边看学生答案边讲，会被学生的错路带偏（这正是旧链路失败的原因） |
| **先验证再开口** | 没验证就讲，等于教一个可能是错的东西。已实测：喂 5 份错解，验证器 5/5 拦下 |

## 3. 核心流程：生成某一小问的思路

### 3.1 五步（对应决策 061 档 3，缩小到单小问）

```
① 切分 ──→ 确定「这一小问」的：
             · 题面（整题 + 该小问的设问）
             · 学生的作答片段
             · 该小问是否被判错

② 求解 ──→ AI 独立做这道小问
             · 不看学生答案（防带偏）
             · 开思考（thinking: enabled）
             · 要求每步写完整推导，禁止「易得」「显然」

③ 验证 ──→ 逐步核查求解的每一步
             · 不看结论对不对，看每一步是否成立
             · 代码按返回字段裁决（不是模型自己说成立就成立）

④ 思路 ──→ 只有验证通过才生成
             · 3~6 步，每步 have / lack / why / do
             · 每步标数学思维（名字取自 54 项，只留名字）

⑤ 缓存 ──→ 存入 questions.subThinking[]
             · 同一小问再点，直接读缓存
```

### 3.2 为什么要「不看学生答案」

决策 061 原文：

> **为什么必须"独立求解"**：如果看着学生的过程去解，会被学生的错误思路带偏 —— 这正是旧链路失败的原因。

实测印证（`开发经验.md` §6.29）：旧链路把"读过程 + 判对错 + 找错因"塞进一次调用，模型跳过计算、凭形式判断，把 `(y-x)/xy + (x-y)/xy` 算成 `2(y-x)/xy`。

### 3.3 验证不通过怎么办

```
验证 overall = "成立"
  → 正常出思路

验证 overall = "部分成立"
  → 出思路，但顶部标注：
    「这一问我证得不够严（第 N 步），补全后结论成立」
  → 依据：2026-10-18 反向测试中，C1 就是这种情况（漏了 u=-1），
     验证器的判断是对的，不该藏起来

验证 overall = "不成立"
  → 不出思路
  → 显示：「这一问我也没做稳」，只给「一种走法」参考
  → 依据：决策 061 §5 "3 次全失败 → 诚实承认"
```

**重试策略**：验证不成立时重试最多 2 次（共 3 次），每次要求 AI 自查上一版的错。仍失败则诚实降级。

## 4. 小问切分（splitter）

### 4.1 为什么这是难点

学生作答和 `referenceProcess` 都可能没有小问标记：

| 情况 | 例子 | 处理 |
|---|---|---|
| 有显式标记 | `(1)…(2)…(3)…` | 按标记切 |
| 无标记但可推断 | 「先证 x+y∈M」「再证 xy∈M」 | AI 判断边界 |
| 双栏作答 | 第 17 题：左栏划掉、右栏修正 | 只取右栏（修正版） |
| 完全切不出 | 短答题、单问 | **整题作为一问**（subNo = "全题"） |

### 4.2 切分实现

```js
// lib/subThinking/splitter.js
async function splitSubQuestions({ call, questionText, studentWork, referenceProcess, segments })
  → [{ subNo: '(1)', ask: '判断 -1∈M…', studentWork: '…', refSteps: [...], isWrong: false }, ...]
```

**规则**：
- 优先用 `questionText` 里的 `(1)(2)(3)` 作为**权威切分点**（题面最可靠）
- 学生作答按同样编号对齐；对不齐则按「AI 判断 + 段落数」对齐
- 切分失败 → 单元素数组（整题），并记 `splitFallback: true`

**容错**：切分结果必须通过校验
- 每个小问的 `ask` 非空
- 小问数量 ≤ 6（超过视为切分错误，退化为整题）
- 所有 `studentWork` 拼起来 ≈ 原文（不能凭空丢内容）

### 4.3 报告页怎么用切分结果

```js
// report.js applyReport() 内
const subQuestions = splitForDisplay(q);   // 前端也有一份轻量切分（仅按 (1)(2)(3) 正则）
```

**注意**：前端切分只用于**渲染入口位置**，不做 AI 判断；真正的 AI 切分在后端生成时再做一次（以题面为准）。

## 5. 数据设计

### 5.1 新增字段：`questions.subThinking[]`

```js
{
  subNo: '(3)',                    // 小问编号；切不出时 "全题"
  ask: '证明：若 x，y∈M，则 x+y∈M 且 xy∈M',
  verified: 'pass' | 'partial' | 'fail',
  verifyNote: '第2步平方封闭漏了 u=-1 情形',   // partial/fail 时必填
  solution: {                       // AI 独立求解
    answer: '加法封闭与乘法封闭均成立',
    steps: [{ step: '…', math: '…', selfCheck: '成立' }],
  },
  thinking: {                       // 给学生的思路
    goal: '…',
    steps: [{
      n: 1,
      have: '…', lack: '…', why: '…', do: '…',
      thinking: { cards: ['转化策略'], say: '…' },   // cards 只存名字
    }],
    ending: '…',
  },
  model: 'deepseek-v4-flash',
  elapsedMs: 60234,
  generatedAt: '2026-10-18T…',
  followUps: [                      // 追问记录
    { role: 'student', text: '…', at: '…' },
    { role: 'ai', text: '…', at: '…' },
  ],
}
```

**为什么存进 `questions` 而不是独立集合**：
- 一题最多 6 条小问记录，体积可控
- 读报告时一次 `get` 就够，不多一次查询
- 与现有 `segments` / `referenceProcess` 同生命周期

### 5.2 复用字段：`questions.revisions[]`

诊断更正的留痕（PRD §5.2 已定义）。**该字段已存在**（决策 063 引入）。

### 5.3 只读字段清单（后端必须校验）

```js
// lib/subThinking/corrector.js
const READONLY_FIELDS = [
  'errorType', 'processScore', 'errorLevel', 'errorDimension',
  'segments', 'breakpoint', 'processAvailable',
  'officialScore', 'officialStatus', 'officialStandardScore',
];
```

**校验逻辑**：任何 `subCorrectDiag` 请求，`field` 必须命中白名单
```js
const WRITABLE = ['diagnosis.comment', 'diagnosis.inference', 'diagnosis.hook'];
if (!WRITABLE.includes(field)) return fail(403, '该字段不可修改');
```

## 6. 接口设计

### 6.1 `subThinking` — 生成某一小问的思路

**请求**
```js
{ action: 'subThinking', questionId, subNo, userId }
```

**响应（成功）**
```js
{ code: 0, data: { subNo, verified: 'pass', thinking: {...}, cached: false } }
```

**响应（验证不通过）**
```js
{ code: 0, data: { subNo, verified: 'fail', verifyNote: '…', thinking: null } }
```

**幂等**：同一 `(questionId, subNo)` 已有 `verified=pass` 的记录 → 直接返回缓存，`cached: true`

### 6.2 `subFollowUp` — 追问

**请求**
```js
{ action: 'subFollowUp', questionId, subNo, userId, text }
```

**响应**
```js
{ code: 0, data: { reply: '…', correction: null | { field, before, after, evidence } } }
```

**不带轮数上限**（用户拍板），但：
- 每次都把完整对话史传给模型
- 单次响应超时 30s

### 6.3 `subCorrectDiag` — 更正诊断文案

**请求**
```js
{ action: 'subCorrectDiag', questionId, subNo, userId, field, newText, evidence }
```

**响应**
```js
{ code: 0, data: { updated: true, revision: {...} } }
```

**必须校验**：
1. `field` 在白名单内
2. `evidence` 非空（说明原诊断错在哪）
3. 写入 `revisions[]` 后才更新 `diagnosis`

### 6.4 `subThinkingGet` — 读缓存（报告页首次渲染用）

**请求**
```js
{ action: 'subThinkingGet', questionId }
```

**响应**
```js
{ code: 0, data: { list: [{ subNo, verified, thinking, followUps }] } }
```

**为什么单独一个**：报告页打开时要知道"哪些小问已经生成过"，但**不能触发任何生成**（零成本原则）。

## 7. 提示词设计

### 7.1 三份 prompt（本次新建）

| 文件 | 作用 | 关键约束 |
|---|---|---|
| `prompts/sub-solve.txt` | 独立求解该小问 | 不看学生答案；禁止「易得/显然」；每步写完整推导 |
| `prompts/sub-verify.txt` | 逐步验证 | 不看结论对错，只看每步是否成立；专门查循环论证/条件用错/非零漏检/跳步 |
| `prompts/sub-think.txt` | 生成思路 | 3~6 步；每步 have/lack/why/do；数学思维取自 54 项名字；禁止通法 |

### 7.2 已验证的 prompt 内容

三份 prompt 均已在 2026-10-18 实跑验证：

| 环节 | 实跑结果 |
|---|---|
| 求解 | 第 19 题 (1)(2)(3) 全部解出，各自 3~6 步 |
| 验证 | 5 份错解 5/5 拦下；2 份正解中 1 份判「部分成立」经核实正确 |
| 思路 | 每问 3~5 步，四要素齐全，数学思维标注准确 |

**结论**：prompt 内容**沿用已验证版本**，不重新设计。

### 7.3 禁止事项（来自决策 061 §8 教训）

> **在提示词里举具体数学例子 = 污染推理。**

实测：备选方案曾写「如 有序对 243+243-32=454 → 211」，模型被数字带偏，连算三轮都是 243。

**规定**：三份 prompt 中**不得出现任何具体数学例子或数值**。

### 8.2 状态机

```
[未生成] --点击--> [生成中] --成功--> [已展示]
                        |
                        +--验证失败--> [失败提示]（可重试）
[已展示] --追问--> [追问中] --回复--> [已展示]
                        |
```

- 入口**默认不触发任何请求**
- 生成中显示进度（复用现有 `reportProgress` 风格）
- 追问**不截断历史**，但每次请求传全量对话
- 并发保护：同一 `(questionId, subNo)` 生成中禁用入口

## 9. 成本与性能

### 9.1 实测数据（2026-10-18，第 19 题）

| 小问 | 求解 | 验证 | 思路 | 合计 |
|---|---|---|---|---|
| (1) | 2.2s | 1.4s | 6.7s | ~10s |
| (2) | 3.0s | 1.7s | 8.1s | ~13s |
| (3) | 28.3s | 14.0s | 17.5s | ~60s |

**单小问 3 次模型调用**，与 PRD §5.3 一致。

### 9.2 成本控制

| 措施 | 说明 |
|---|---|
| 不点不生成 | 默认零调用 |
| 思路缓存 | 同一小问二次点击命中缓存 |
| 并发生成锁 | 同一小问不允许并发生成 |
| 成本埋点 | 记录每次调用的 token 与耗时 |

### 9.3 超时

| 环节 | 超时 |
|---|---|
| 单小问生成 | 90s（实测最长 60s） |
| 追问单轮 | 30s |

**已核实**：`reportService/config.json` 的 `timeout: 900`（15 分钟），远超单小问 90s 需求。
