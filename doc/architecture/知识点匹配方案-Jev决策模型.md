# 知识点匹配方案（Jev 决策模型）· 实测定稿

> 状态：**待审**（未动代码）
> 日期：2026-10-05
> 依据：2026-10-04~05 全部实测（腾讯 EdgeOne + OpenRouter 双网关 + 本地模型对照）
> 目标：替换现有「字符相似度匹配」，解决系统性错配；同时把成本打下来

---

## 〇、一句话

**用 Jev（TypeSafe System One 决策模型）从受控清单里「选」知识点，而不是让 LLM「写」知识点名，再用字符相似度去猜。**

```
现在：AI 自由写名字 → 字符相似度匹配 → 系统性错配
改成：AI 从清单里选（choice）→ 直接拿 ID
```

---

## 一、现在的问题（实测数据）

### 1.1 现在的做法

`cloudfunctions/graphEngine/src/lib/knowledgeMatch.js`

```js
function simName(a, b) {
  // 字符重合度（含 includes 分支）
}
async function findNode(kName) {
  // 遍历全部节点，取相似度最高者，门槛 0.8
}
```

### 1.2 实测的失败模式（**不是偶尔错，是系统性塌陷**）

用线上 61 道题的 `knowledgeUsage` 实测（83 个知识点条目）：

| AI 判出的名字 | 字符匹配结果 | 相似度 | 对错 |
|---|---|---|---|
| 集合的并集 | 集合 | 0.760 | ❌ 应匹配「并集」 |
| 集合的交集 | 集合 | 0.760 | ❌ 应匹配「交集」 |
| 集合的运算 | 集合 | 0.760 | ❌ |
| 集合的包含关系 | 集合 | 0.714 | ❌ 应匹配「属于与包含的关系」 |

**关键：所有带"集合"的长名字，全部塌到「集合」这一个节点上。**

**后果**：集合节点承接所有集合相关题的账 → attempts 虚高、mastery 被稀释；而「并集」「交集」这些真正的考点，账是空的 → 聚合到父节点后，整个第一章的 K 结构是错的。

### 1.3 量化

```
知识点级匹配成功率：67/83 = 80.7%
题级能定出 unitName：15/19 = 78.9%
近失（0.6 ≤ sim < 0.8）：13 条  ← 全被门槛挡掉
```

**且 `includes` 分支的分数上限被卡在 1.0 以下**：

```
"集合" ⊂ "集合的运算"
short=2, long=5
0.6 + 0.4 × (2/5) = 0.76   ← 永远够不到 0.8
→ 越短的名字（越基础的概念）越容易被挡掉
```

## 二、方案（实测验证）

### 2.1 两阶段选择

```
阶段一：判章节
  state     = 题目文本
  type      = choice
  criteria  = 6 个章节名 + 「其他/都不是」
  输出      = 章节 + conf

阶段二：章内选知识点
  state     = 题目文本
  type      = choice
  criteria  = 该章的节点（≤81 个）+ 「其他/都不是」
  输出      = 知识点 + conf

后处理（纯代码，0 成本）：
  conf ≥ 0.9        → 直接记账
  0.4 ≤ conf < 0.9  → 记账但标注「待确认」
  conf < 0.4 或选中「其他」 → 进 node_requests 待建队列
```

### 2.2 为什么分两阶段

```
① 271 个节点超过 Jev 的 255 候选上限（实测报错：supports 1-255 options）
② 分章后最大一章 81 个候选，远低于上限
③ 阶段一顺带产出「章节」，而 updateMastery 正需要 unitName 才能给 A 记账
④ 成本更低（见 §4）
```

章节分布（实测）：

| 章节 | 节点数 |
|---|---|
| 第0章 预备知识 | 12 |
| 第一章 集合与常用逻辑用语 | 58 |
| 第二章 一元二次函数、方程和不等式 | 31 |
| 第三章 函数的概念与性质 | 41 |
| 第四章 指数函数与对数函数 | 48 |
| 第五章 三角函数 | 81 |
| **合计** | **271** |

### 2.3 更好的方案（实测支持，待定）

**`knowledgeUsage` 本来就是 1~5 个知识点，而 `choice` 是互斥单选。**

官方 cookbook 推荐的做法：**choice 选主分类 + 每个 tag 一个 noul**

```
questions: {
  main:  choice  → 主知识点（互斥）
  tag_1: noul    → 是否还考查「集合」
  tag_2: noul    → 是否还考查「元素」
  ...
}
```

**实测结果**（并集题）：

```
主 choice → 并集 (conf 1.00) ✅
noul 命中: 集合:0.99  元素:0.82  并集:0.99  互异性:0.82  无序性:0.54
```

**优势**：同一次请求内并行求值，成本不增加；且天然表达"一道题用到多个知识点"。

**待定**：是否用这个替代单 choice（需要再测准确率）。

## 三、实测数据（双网关交叉验证）

### 3.1 准确率与置信度

| 候选数 | 腾讯 EdgeOne | OpenRouter | 说明 |
|---|---|---|---|
| 12 | 100% / conf 0.998 | 100% / conf 0.998 | 完全一致 |
| 30 | 100% / conf 0.998 | — | |
| 60 | 100% / conf 0.996 | 100% / conf 0.994 | |
| 120 | 100% / conf 0.994 | — | |
| 254 | 100% / conf 0.992 | 100% / conf 0.994 | 接近上限 |
| **271** | **❌ HTTP 400** | — | **超 255 上限** |

**关键：从 12 到 254 个候选，准确率完全不变（100%），置信度只从 0.998 降到 0.992。**
（这与预期相反 —— 候选增多并不会让 Jev 混淆）

### 3.2 两阶段策略

```
阶段一（判章节）：5/5 全对，conf 1.00
阶段二（章内选点）：5/5 全对，conf 0.99~1.00（58 候选）
```

### 3.3 对照：其他方案

| 方案 | 稳定度 | 准确率 | 备注 |
|---|---|---|---|
| **Jev（本方案）** | **86~100%** | **100%** | 读 logits，确定性推理 |
| 本地 Intern-Decision-0.8B | 100% | **25%** | M1 8GB 能跑（791ms/次），但太小 |
| DeepSeek V4.1 自由写名字 | **4%** | — | 措辞每次都变 |
| DeepSeek V4.1 只输出序号 | 75% | — | prompt 约束后改善 |
| 字符相似度（现状） | — | 80.7% | **系统性错配** |

**本地模型实测细节**：M1/8GB 能加载（30s）并推理（786~971ms），置信度仅 0.22~0.39（接近随机），
4 题对 1 题。**结论：0.8B 不够用，4B 才够（但 8GB 跑不了）。**

## 四、成本（实测）

### 4.1 Jev 定价

```
输入：$0.042 / 百万 token
输出：免费          ← 关键
上下文：32,000 token
候选上限：255
```

实测验证（4 候选简单题）：
```
输入 417 tok / 输出 49 tok / cost $0.00001751
→ 精确等于 $0.042/M ✅，输出确实免费 ✅
```

### 4.2 单题成本

| 方案 | token | 成本/题 |
|---|---|---|
| Jev 12 候选 | 1,259 | $0.000053（¥0.00038） |
| **Jev 两阶段**（500 + 5,045） | ~5,545 | **$0.000233（¥0.0017）** |
| Jev 60 候选 | 5,045 | $0.000212（¥0.0015） |
| Jev 254 候选（单阶段全量） | 25,187 | $0.001058（¥0.0075） |

### 4.3 对比原方案

| 环节 | 输入 | 输出 | 成本 |
|---|---|---|---|
| DeepSeek 全清单直选（做匹配） | 825 | **3,034** | **¥0.0134 ~ 0.0267** |
| **Jev 两阶段** | ~5,545 | 0 | **¥0.0017** |
| **省** | | | **6x ~ 12x** |

**原方案 86% 的成本花在「输出」上** —— 因为让 AI 写知识点名字（30+ 汉字 = 3000+ token）。

### 4.4 余额测算（$5 = ¥36）

```
$5 能跑约 14,000 题
   = 约 737 批（每批 19 题）
   = 约 14.7 个学生的一学期用量

对照原方案：$5 只能跑 1,180 ~ 2,360 题
```

## 五、落地要点（实测踩过的坑）

### 5.1 question id 必须是英文/合法标识符

```
❌ 报错：Invalid Jev System One question id: 集合
✅ 用 k1 / k2 / tag_1 ...
   然后代码里映射回中文名
```

**注意：`criteria` 的选项名可以是中文（实测可行），只是 question id 不行。**

### 5.2 候选上限 255

```
HTTP 400: supports 1-255 options
→ 271 个节点必须分章
```

### 5.3 上下文 32k

分章方案用 ~5.5k token，充裕。全量 254 候选用 25k，接近上限。

### 5.4 网关选择

| | 腾讯 EdgeOne | **OpenRouter** |
|---|---|---|
| 端点 | `ai-gateway.edgeone.link/v1/systemone` | `openrouter.ai/api/v1/systemone` |
| 模型 | `@makers/jev` | `typesafe/jev-1.13` |
| 计费 | 共享免费额度 | **输入计费，输出免费，响应带 `usage.cost`** |
| 生产可用性 | 上不了生产 | ✅ **TypeSafe 官方推荐渠道** |

**结论：生产用 OpenRouter。**

### 5.5 置信度是可靠的筛选器

实测中置信度与"答案可靠性"高度相关：

```
conf 1.00  → 并集/交集/补集/元素关系（全对）
conf 0.99  → 确定性（对）
conf 0.55  → 互异性（对，但模型自己不确定）
conf 0.47  → 无序性（题目本身有歧义：无序性 vs 集合相等，两个答案都对）
```

**模型自己"知道"哪里不确定 —— 这天然解决了"该不该信任这条判定"。**

## 六、顺带发现的问题（不属本方案，但要记录）

### 6.1 `node_requests` 是 0 条（查清了，不是 bug 但是设计缺陷）

```js
// updateMastery.js:41-44
const countsForK = (Pkp === 1) || (lvl === 'concept');
if (!countsForK) continue;                    // ← 先过滤
const nodeId = await matchKnowledgeNode(...); // ← 只有通过过滤的才走匹配
```

**后果：只有 P=1 或 concept 错的知识点才会走匹配 → 才可能进待建队列。**

```
→ rule/skill 类错误涉及的新知识点，永远进不了待建队列
→ 图谱缺口被系统性漏掉：只有在"学生做对了"时才能发现缺节点
```

**次级问题**：写入失败只 `console.warn`，不落库不重试 → 云函数日志不留存 → 静默失败。

### 6.2 图谱结构问题（另一条线）

```
reference（前置依赖）覆盖率 56%
跨节引用只有 42/561 = 7.5%   ← 溯源走不出去
21 条悬空引用（指向不存在的节点）
parent_id 全是 null（靠中文 path 字符串）
```

### 6.3 K 的口径未更新

```
statService/kFormula.js 用的是决策 052 口径（纯对率，难度不进）
而 2026-10-03 定的是 060 口径（难度进权重 0.1/0.2/0.7）
→ 前端显示的 K 与定义不符
```

### 6.4 `updateParams` 还在写已废字段

```js
// judgeOne/index.js:559-584
patch.fiveDim = params.fiveDim;      // 决策 051 已删
patch.isCorrect = params.isCorrect;  // 决策 051 已停写
await migrateProgress(...);          // 旧口径迁移
```
