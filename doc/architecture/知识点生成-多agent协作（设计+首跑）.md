## 0. 大白话

「知识点生成」现在有**两条互不相通的链**：

1. **建库链（离线，7 月一次跑完）**：教材 PDF → MinerU → 按节拆 → **agent1 版面 → agent2 提取 → agent3 质检** → 转 schema → 入库（271 节点）
2. **运行时链（每次判定）**：题干+痕迹 → **一次生成**知识点名 → `findNode` 相似度 ≥0.8 匹配 → **没匹配上就 `custom_nodes` 兜底自造**（已 39 条）→ K 记账

外加一条**已实现但没接入**的：**D2 拆考点节点**（模型→代码→模型，含「编号勾选」）。

**问题全在第 2 条**：模型自由命名 → 匹配门槛挡掉 → 兜底自造 → **同一内容分裂成两个节点，掌握度被摊薄**。

## 1. 多 agent 协作设计（四条原则）

> 常见多 agent 的通病：三个模型互相「同意」，一起漂。所以这里**每个角色都有代码收口**，且 **agent 之间不互相改稿**。

```
题干 + 痕迹
  ├─ Agent A 提议者 ──► 候选知识点（自由命名，宁多勿漏）            1 次调用
  ├─【代码】映射裁判 ──► 相似度映射到「知识区 182 节点」的编号（≥0.8，同线上门槛）
  ├─ Agent B 校验者 ──► 只看 题干 + 候选(编号+节点名+教材原文)：逐条 keep/reject
  │                    **禁止新增或改写名字**                        1 次调用
  ├─【代码】收口 ──► keep 的按编号回填名字；全空 → 触发 C
  └─ Agent C 裁决者（仅必要时）──► 判「命名不同」还是「图谱真缺」；真缺 → 出待建提案，**不写库**
```

四条原则：① **编号优先**（名字由代码回填，可复现）② **代码当裁判**（相似度/白名单/门槛都由代码定）③ **不许改名**（B/C 只能投票或裁决，不能改稿）④ **C 不写库**（只出提案，防自动灌库）

## 2. 首跑证据（3 道真题，`scripts/kb-agents.mjs --source=db --limit=3`）

| Agent A 提议 | 代码映射结果 | 结论 |
|---|---|---|
| **集合的交集** | **0.76 → 被 0.8 门槛挡掉** | 历史落库值是「**交集**」——**同一内容差 0.04 没匹配上** |
| **集合的并集** | **0.76 → 挡掉** | 历史落库值「**并集**」 |
| 数轴法求集合运算 / 区间的端点取舍 | 0.7 / 0.364 | **本就不该是知识点**（WWH 里「不建」的方法类） |
| 集合元素的互异性与列举法 | 0.7 | 长名+混合，需归一 |
| 一元二次方程 | 0.867 fuzzy ✅ | **Agent B 投 keep**（理由：需解 x²−3x+2=0 求集合 A 元素） |
| 空集 | exact 1 ✅ | **Agent B 投 keep**（理由：条件 A∩B=∅ 涉及空集概念） |

### 病灶 1：**匹配门槛把「正确的归一」挡在门外**（最要命）

`simName` 对「短名是长名子串」只给 `0.6 + 0.4×(短/长)`：「交集」⊂「集合的交集」→ `0.6+0.4×(2/5) = 0.76` < 0.8 → **匹配失败 → 兜底自造**。
**这解释了 `custom_nodes` 那 39 条是怎么来的**（模型爱说「集合的XX」，而图谱名是「交集」）。

### 病灶 2：**提议形态偏「长名 / 方法化」**

模型倾向输出「集合的并集」「数轴法求集合运算」「区间的端点取舍」——前一类是**同一概念的啰嗦说法**（该归一），后一类是**方法/套路**（按决策 028 该挡）。前者靠代码归一，后者靠 Agent B 过滤。
