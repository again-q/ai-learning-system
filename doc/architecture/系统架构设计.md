## 二、组件职责

### 1. 诊断引擎（Diagnosis Engine）
- **类型**：AI 驱动，无对话
- **可见性**：纯后台，学生不可见
- **数据源**：拍照录入模块输出的结构化题目、学生作答
- **能力**：
  - 识别题目所属知识点（关联 knowledge-graph 节点）
  - 判断学生作答对错
  - 分析错误类型（K/A/T/Q/S 维度归因）
  - 更新学生的五维掌握度数据
  - 更新 knowledge_progress 和 mastery_logs 集合

### 2. 知识图谱管理员（Knowledge Manager）
- **类型**：AI Agent，可对话
- **可见性**：学生可见
- **权限**：只读（不能修改知识图谱数据）
- **能力**：
  - 回答"我目前哪些知识点掌握了？"
  - 回答"我哪些知识点薄弱？"
  - 展示五维能力雷达图
  - 按章节/知识点维度查询掌握度
  - 不参与训练计划制定

### 3. 个性化学习教练（Learning Coach）
- **类型**：AI Agent，可对话
- **可见性**：学生可见
- **数据来源**：从知识图谱（诊断引擎更新的掌握度数据）读取学生状态
- **能力**：
  - 根据薄弱点制定训练计划
  - 推荐练习题
  - 分析做题数据，给出学习建议
  - 不直接修改知识图谱

### 4. 拍照录入模块（Photo Intake）
- **类型**：功能模块，非 AI Agent
- **可见性**：学生可见
- **能力**：
  - 学生拍照上传（选择题/填空题/解答题/作答笔记）
  - 多模态 AI 识别 → 结构化题目数据
  - 送入诊断引擎处理
- **难点**：拍照格式不固定，需要多模态视觉模型

## 五、设计原则

1. **职责分离**：三个 AI 角色各管一摊，Prompt 专注，质量可控
2. **诊断引擎后台化**：无论题目来源（拍照/手动/导入），走同一条 pipeline
3. **管理员只读**：学生可查不可改，保证五维评分的可信度
4. **模块化输入**：拍照录入只是诊断引擎的数据来源之一，不是唯一方式

## 六、项目未来全景

### 用户的一天

```
课间 3 分钟             打开小程序
                        ↓
                 知识管理员弹出一条提醒：
                 "你昨天做的集合题错了2道，
                 来，说说交集和并集有什么区别？"
                        ↓
                 学生回一句 → AI追问 → 2-3轮
                 → 想通了，关手机
                        ↓
                 晚上自习                  
                 学习教练：
                 "集合的薄弱点还没完全巩固，
                 来做3道题巩固一下"
                        ↓
                 拍照录入 → 诊断引擎更新
                 → 掌握度从 60% → 75%
                 → 管理员明天继续追踪
```

### 认知科学的核心机制

两个 Agent 不是 Chatbot，而是**认知工具**：

| 机制 | 谁实现 | 效果 |
|------|--------|------|
| **苏格拉底式追问** | 知识管理员 | 引导学生自己发现盲区，不是直接给答案 |
| **间隔重复提醒** | 学习教练 | 根据遗忘曲线，在恰当时间推送复习 |
| **元认知训练** | 知识管理员 | "你觉得你懂了，但真的懂了吗？" |
| **能力归因** | 诊断引擎 | 不是简单说"错了"，而是"这是K问题还是A问题" |
| **成长可视化** | 知识管理员 | 看到自己从 40% → 65% → 80% 的进步轨迹 |
