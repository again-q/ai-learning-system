## 0. 大白话

线上判一道题是「一个 800 行函数从头干到尾」。D4 = 把这 8 件事拆成 8 个小盒子，用传送带按顺序串起来；每个盒子喂进去一份数据、吐出一份数据，**顺序、字段、降级行为都和线上完全一样**。

目的不是"改好"（那是 D6/D7/D8 的事），而是**先让新引擎能跑出和线上一模一样的结果** —— 这样 D5 才能用"0 差异"当切换闸门。

## 1. 图拓扑（**这条就是 D3 设计里唯一未定的 G**）

```
START
  → N0 loadQuestion     取题 + 归属校验（读 questions）
  → N1 ragLookup        历史参考注入（自动；searchHistory → buildRagContext）※ 非点击触发的那个
  → N2 judgeAI          AI 一口气判定（行为同线上 judgeQuestion）
  → N3 normalize        纯程序整理：钳制 + 空白防毒 + errorType/Level 推导 + pattern 拼接
  → N4 persistQuestion  写 questions（约 20 字段）
  → N5 updateMastery    掌握度 K/A + knowledge_progress
  → N6 ragLog           mastery_logs（含 embedding / reportText / report 快照）
  → N7 batchProgress    batches.progress / completed
END
```

- **串行**，不并行：N5/N6/N7 都依赖 N4 的结果；并行省下的几百毫秒不值得牺牲失败隔离与可比性
- N3 是纯程序节点（无 IO），最先落地、最好测（对应迁移计划 P0 说的"先切纯程序段"）

## 2. 每个节点（输入 / 输出 / 类型）

| 节点 | 做什么 | 输入 | 输出 | 类型 |
|------|--------|------|------|------|
| **N0** | 取题、校验归属 | `questionId, openid` | `question` 文档 | DB |
| **N1** | 翻旧账：找最像的历史题 + 拼 RAG 上下文 | `questionText, openid` | `ragContext`（字符串） | DB+RAG |
| **N2** | AI 判定（难度/得分/知识点/卡壳/错因/过程分段…） | `question, ragContext` | `raw`（模型 JSON） | **AI** |
| **N3** | 纯程序整理：`clampParams` 钳制、空白题归因由代码推导、`errorType`/`errorLevel` 防御回退、选填题不许"过程风险"、pattern 三层拼接 | `raw, question` | `clamped {D,P,eta}` + `derived {errorType,errorLevel,errorAttribution,patternText,patternFull}` | 纯函数 |
| **N4** | 写库 `questions` | 上面全部 | 无（副作用） | DB |
| **N5** | 掌握度更新（K 知识点粒度 + A 单元级 + `knowledge_progress`） | `raw, clamped, question` | `{mainNodeId, pOk}` | DB |
| **N6** | 写 `mastery_logs`（旧题库/检索源，含 embedding） | 上面全部 | 无（副作用，**失败降级不阻塞**） | DB+向量 |
| **N7** | 批次进度：`done+1`，够了就 `completed` | `question.batchId` | 无（副作用，**失败降级**） | DB |

## 3. 状态（LangGraph State channels）

```
{ questionId, openid,
  question,           // N0 产出
  ragContext,         // N1 产出
  raw,                // N2 产出（模型原始 JSON）
  clamped, derived,   // N3 产出
  mastery,            // N5 产出 { mainNodeId, pOk }
  issues: [] }        // 各节点的非致命问题（降级/回退都记这里，不静默）
```

## 5. 行为一致性约束（D4 的红线）

1. **不改 AI 调用方式**：N2 仍是"一次大 JSON"（与线上同 prompt、同 disabled/低温）→ 变化只来自"壳"，不来自"芯"
2. **不改阈值与推导规则**：空白判定、errorType/Level 回退表、选填题禁"过程风险"、clamp 阈值全部照抄
3. **降级语义照旧**：N6/N7 失败只记 `issues` + warn，不阻塞主流程
4. **不碰线上**：新图在 `graphEngine` 里，旧 `judgeOne` 一行不改

| **A** | 图拓扑：串行 vs 并行 | ✅ **串行** | ① N6 要用 N5 产出的 `mainNodeId`，本就不可并行；② N7 只是一次 DB 读写（百毫秒级），在整题 AI 判定（秒级）面前可忽略；③ 并行会让时序不确定 → 影子对比难复现，且 LangGraph 多分支写同一 state 还要额外设计 reducer |

| **D** | 线上函数怎么办（会不会与新节点重复） | ✅ **步骤逻辑搬进节点，底层工具先复制后收敛** | 见下方「D 的澄清」——`clampParams`/`updateMastery` 这类**是节点的实现内容，不是另外的工具**，搬进 N3/N5 后旧的那份随旧代码一起在 D5 后废弃；只有跨节点共用的**底层工具**（图谱匹配/标尺文本/RAG 检索）才存在"先复制后收敛" |

### D 的澄清：什么算"搬进节点"，什么算"复制一份"（用户 2026-09-19 提问）

结论：**不是所有东西都"复制一份"，方向是"搬走"**。区分两类：

| 类别 | 例子 | 处理 | 过渡期是否会两份并存 |
|------|------|------|------------------|
| **步骤逻辑**（就是节点的实现内容） | `clampParams`（钳制）→ 属 **N3 整理归一**；`updateMastery`（掌握度 K/A + knowledge_progress）→ 就是 **N5** | **搬进节点**：N3 = `src/lib/normalize.js`（已落地 99 行）；N5 = `src/nodes/updateMastery.js` | 短暂并存（旧代码 D5 前还要跑），**但新图不引用 judgeOne 任何代码**；D5 切换后旧的那份删除 |
| **底层共用工具**（跨节点复用，不是业务步骤） | `matchKnowledgeNode` / `findNode` / `unitNameOf`（图谱匹配）、`RUBRIC` 标尺文本、`searchHistory`（RAG 检索） | **先复制进 `graphEngine/src/lib/`**，文件头标注来源 `judgeOne@<commit>` | 是（不可避免），D5 切换后收敛成共享包 |

**为什么要这么分**：
- 步骤逻辑如果"抽成共享库"，等于让新节点去依赖线上大函数，反而破坏"盒子自治、可单测"（盒子应自己拿着实现，外部只注入 db/llm/kg）
- 底层工具是纯技术能力（匹配/检索/标尺），与业务步骤无关，才适合共享

**防漂移的硬规则**：新图**不 require `judgeOne` 的任何文件**；D5 对拍以**线上落库值**为准；D5 切换后删除旧判定代码，两份自然收敛成一份。
### 关于 A 的补充：并行看起来快，其实不划算

- 整题判定的耗时几乎全在 **N2（AI 调用，几秒）**；N4–N7 的 DB 读写加起来是几十到一两百毫秒级
- 真正值得并行的场景是 **D7/D9**（批量多题、断点续跑）——那时用「多题并行」，收益才明显
- 单题内并行只会让失败路径与 state 合并复杂化，违背 D4「行为一致、可比」的目标
