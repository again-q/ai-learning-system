## 3. 重大问题（按「会不会误导学生 + 影响面」排序）

### P1 · 精细数值不可复现，但被当精确分数用（最高）
- 证据：同题重跑 D `0.65→0.62`、P `0.4→0.5`、η `0.5→0.6`（D4 实测）；D3 冒烟三轮 η `0.3/0.3/0.5`；生产库 **35%（13/37）** 的 P 是 `0.15/0.55/0.85` 这类连续小数。
- 影响：P 本身前端不显示，但**掌握度变化百分比** = Σ(D×P)/ΣD（updateMastery.js:36,80）→ 抖动直接传到「掌握度 72%→75%」这种展示上。
- 建议：展示层改成**档位/区间**（对 / 半对 / 错，或 P 三档），把连续值留给内部分析；D5 影子对拍先把「抖动带」量出来。

### P2 · η 没有区间钳制，却直接进掌握度公式
- 证据：`clampParams` 对 η 原样透传（graphEngine/src/lib/normalize.js:20-21；线上 judgeOne 同款），标尺要求 0.4~1.0（D难度标尺-L11分层.md:77）；`updateMastery.js:110-132` 用 `eff = D×η×(2P-1)`，且有 `η>=0.7` 加分 / `η<=0.6` 扣分分支。
- 影响：η 抖 0.2（0.6 与 0.7）**正好跨过加分/扣分边界**，一次判定就能决定某知识点涨还是跌。
- 建议：η 按标尺钳区间；边界分支改成连续函数（不要卡在 0.6/0.7 的悬崖上）。

### P3 · 决策 043 的三问判据没有落到线上判定（两套口径并存）
- 证据：线上 judgeOne 的 prompt（逐字抽取在 graphEngine/src/lib/prompts.js）里 `noEvidence` 出现 **0 次**；新节点 judgePoints.js 里出现 **7 次**。
- 影响：同一件「考点给几分」，整题判定用旧口径、环节判定用决策 043 的新口径 → 结论可能不一致；D5 影子对拍一定会撞上。
- 建议：把 043 判据同步进整题判定 prompt（属于 D6 拆 AI 的前置）。

### P4 · RAG 把上一次的判定回注给这一次（误差自我强化）
- 证据：`searchHistory` 查学生自己的 `mastery_logs`（含上次判分/归因）拼进 prompt（judgeOne/index.js:269-288, 614）。
- 影响：判偏一次，后面更容易继续偏（自我确认）。
- 建议：D5 加一组 A/B（有/无历史注入）量化差异；或改成只注入「题干+结论」不注入上次的判分与归因。

### P5 · 模型漏给错误层级时，一律说成「粗心」；errorDimension 是死字段
- 证据：兜底链最后一项固定 `skill`（judgeOne/index.js:647-650）；而它依赖的 `errorDimension` 在生产库 **38/38 全空**（映射表实际不生效）。
- 影响：把「不知道是什么错」写成「计算/审题失误」——与「空白题禁止写未理解」是同一类毛病，但这里没防。
- 建议：拿不到层级时输出 `null`（前端不展示），别默认 skill。

### P6 · 五维 fiveDim 零校验（已修代码 + 已清数据，根因仍在）
- 证据：生产库 4 道题出现 `K=3 / Q=4 / S=3` 这种 **0~5 量纲**（模型量纲不一致），此前直接落库。
- 本次修复：代码层改成**越界或缺维度即整组作废为 null**（不钳成 1，那等于编数据）；库内 4 行 fiveDim 置 null、原始值留档 `fiveDimRaw`。
- 残留根因：prompt 没写清「五维是 0~1」（或干脆改成代码由程序分推导），否则下次还会给 3。

### P7 · 学生端「只给结论不给证据」+ 三个入口点不到
- 证据：`segments.evidence`（学生原话）已入库，前端只渲染 step 摘要（report.wxml:94-97）；`pendingNodes` 15/15 份报告都算了但**前端不渲染**（report.js:247 只存）；`report-dispute-modal` / `report-module` / `report-overview` **全项目零引用**（grep 验证），所以「我有异议」点不到、disputes 表 0 条。
- 影响：学生无法核对结论、无法质疑、看不到「接下来练什么」——9/1 定的「掌握度连带」断在最后一公里。
- 建议：按此顺序补 ① pendingNodes 渲染 ② evidence 原文 ③ 异议入口接回。

### P8 · 报告契约文档失真
- 证据：`doc/architecture/报告JSON结构.md` 仍写 v1（overview/weakpoints），实现已是 summary/masteryChange/pendingNodes/questions（reportService/index.js:570-582）。
- 建议：文档跟着实现更新一次（否则后面每改一处都要重新考古）。

### P9 · 质量无法自证：没有评测集
- 现状：判断「判得准不准」只能靠冒烟 5 类题与个案重跑；`doc/architecture/评测数据集预研.md` 还停在预研。
- 影响：所有「质量」结论都缺一个可复现的分母。
- 建议：用 20~30 道**有标准答案**的题建固定评测集（覆盖选择/填空/解答、空白/半对/全对），每次改 prompt 都跑一遍。

## 6. 更正与补充（2026-09-19 用户追问「参数不会展示给学生吧」后逐页自查）

**结论：原始参数确实没给学生，但参数的加权结果给了。**

| 参数 | 是否给学生看 | 证据 |
|---|---|---|
| P（过程分）原始值 | **否** | 报告页只把它当内部判据用（report.js:296 `wrongQ`），wxml 不渲染 |
| η（路径质量） | **否** | 前端零引用 |
| D（难度值）原始值 | **否**（只给档位 L1–L11） | 报告页不渲染 `difficultyValue`；`review` 复核页是给学生/管理员改参数用的（review.js:261） |
| fiveDim 五维 | **否** | 全项目 grep 零引用 |
| `processScore`（题型轨迹） | **否** | pattern-trajectory.js:18,31 传进 data，但 wxml 不渲染 |
| **掌握度百分比（由 Σ(D×P)/ΣD 算出）** | **是，3 处** | ① 报告页底部「掌握度变化 100% → 83%」（report.wxml:142-146）② **知识图谱页**（tabBar 常驻页）每个知识点 `{{item.mastery}}%`（graph.wxml:46,84,121），数据来自 graphService 的真实 progressMap×100（graph.js:71）③ 我的页学科进度条（目前数据未接，恒 0） |

→ 也就是说：**「参数不展示」这条设计在报告页成立；但它通过「掌握度」间接展示在图谱页与报告页底部**。如果目的是「不让抖动数字进学生视野」，那这两处也该档位化（图谱页本来就有颜色档 mColor，可以只留颜色不留数字）。

## 7. 智学网跑批专项（2026-09-19，为「这一周跑 13 份」专门查的）

### 7.1 两个必须先解决的（否则跑不出东西）
1. **登录态已过期**：`zhixueAuth status` → `{connected:false, expired:true}`；`zhixue_auth` 里那行 cookie（15 项，updatedAt = 今天）已失效。**跑之前必须重新连一次**（账号+密码+真实姓名那条路不需要验证码）。
2. **「原卷图 → 拆题 → 判定」这条链路在智学网图上从未跑通过**：唯一那次 import 只建了批次（`imageCount=1`、`fileIds=1`、status=pending），**该批次题目数 = 0** —— 拆题、裁切、判定一次都没执行过。而原卷是**整张多题大图**，风险点正好落在刚修过的 bbox 裁切那段（此前只在拍照图上验证）。→ **先拿 1 份试跑**，再批量。

### 7.2 其实不必走原卷图：官方逐题数据更全（代码已实现，待登录态恢复后实测）
`zhixueSync detail` 返回（`cloudfunctions/zhixueSync/index.js:159-182`）：
- `topics[]`：**每题官方得分 score/standardScore、官方对错 isCorrect、学生答题卡截图 imageAnswer**
- `wrongTopics[]`：**题干 contentHtml、标准答案 answerHtml、官方解析 analysisHtml、题目图 topicImgUrl、班级得分率 classScoreRate、官方知识点 knowledges**

→ 用官方数据定「对错」，AI 只负责「**为什么错 / 卡在哪一步 / 哪个考点没掌握**」：
① 对错零抖动（不依赖 AI）；② 绕开拆题/裁切这个最大不确定性；③ **班级得分率本身就是「学校情况」的答案**（全班都错 = 没讲透；只有你错 = 你的问题）；④ 官方逐题得分 = 现成的评测集，可直接算系统判定的漏判/误判率（补上 P9 缺的分母）。

### 7.3 会用操作方式卡住你的
- **逐题判定是小程序端循环触发的**（`miniprogram/pages/photo/photo.js:302+`，2 个 worker）→ 13 份 × ~20 题 = 数百次调用，手机得一直挂着复核页。批量请用跑批脚本（本机 `/tmp/prodstats/rerun-all.cjs`：按批次 diagnose + tcb CLI 并发 3 判题）。
- **超时配置**（实测）：diagnose 120s、judgeOne 120s、reportService **900s**、zhixueSync **60s**、photoUpload 20s、graphService 3s（Nodejs16.13）。→ import 要**分批**（内部 4 个一组），别一次塞 13 份。
- **成本估算**：13 份 × （1 次拆题 + 每题 VLM 精读 + DS 判定 + 报告每题诊断 + 1 次总结）≈ 600~800 次调用 ≈ **¥10~30**。

### 7.4 会影响结果解读的（承接 P1–P7）
- **P4（RAG 回注）在这一批上影响最大**：13 份同章同类型卷子连着判，每题都把前面积累的历史当参考 → 系统性偏差会被反复锚定。建议跑批前先做「有/无历史注入」A/B，或临时关闭。
- **P7（pendingNodes 不渲染）**：你要的「快速掌握学校情况」最需要的薄弱点清单（15/15 份都算好了）**前端不显示**。
- **P1/P2**：这批会写大量 `knowledge_progress`，建议先只看「对/半对/错 + 断点 + 错因」，**别把掌握度百分比当趋势**（图谱页又是直接显示百分比的）。
