## 一、项目背景速览

- **产品**：微信小程序 + CloudBase，服务 120+ 学生
- **核心路径**：五维能力框架定稿 ✅ → 知识图谱 356 节点 ✅ → **拍照录入 & 诊断引擎 MVP（当前）** → AI 教练
- **时间线**：目标 9/1 开学前完成 MVP
- **关键技术资产**：五维能力向量框架（K/A/T/Q/S）+ 24节356节点知识图谱 + 统一 schema

## 二、总体架构概览（已定，不在此讨论）

```
📸 拍照上传（1题或多题）
       ↓
① Qwen3.7Plus（图像理解模型，云函数部署）
   整体把握图片：描述题目文字/公式/图表 + 做题痕迹
       ↓  Markdown 报告（自然语言叙述）
② 向量检索（RAG）→ 检索历史同类题记录
       ↓  top-5 相似记录
③ DeepSeek V4 Flash（推理诊断模型，CloudBase TokenHub）
   综合分析：Qwen 输出 + 知识图谱历史 + RAG 结果 + 五维趋势
       ↓
更新数据库（node_progress / mastery_logs / 向量库）
```

**已定决策（不在此讨论）：**
- 诊断引擎拆为两个 AI（图像理解 + 推理诊断），非单一多模态
- 前端放「生成报告」按钮，用户拍完批量触发，不支持逐题出报告
- 规则校验并入 Flash 推理阶段，不另加校验层
- 维护历史趋势（mastery_logs 集合）

## 💡 RAG 是如何进入我们视野的（讨论过程记录）

> 这段记录了讨论过程中的思维链路，帮助后续参与者理解"为什么我们会想到 RAG"，
> 而不只是看到"我们决定用 RAG"这个结果。

### Step 1：先定了双 AI 管线

最初讨论的是诊断引擎怎么设计。很快达成共识：
- 不能用单个多模态模型做到底（成本高、不够灵活）
- **Qwen3.7Plus 做图像理解**（看图、提取文字、观察做题痕迹）
- **DeepSeek V4 Flash 做推理诊断**（分析、评分、出报告）

这是一个感知 → 认知的分工。

### Step 2：讨论"AI 怎么真正懂用户"

确定了管线后，出现了一个更深的问题：

> Flash 推理时，需要读取学生过往数据来做诊断。但历史记录那么多，怎么让 AI 真正"理解"这个学生的状况，而不是生硬地读一堆数字？

这个问题的本质是：**Flash 该以什么形式"看到"学生的历史？**

讨论了几种思路：

| 方案 | 思路 | 问题 |
|------|------|------|
| **方案 A：结构化摘要** | 每次诊断后 Flash 写一段学生画像摘要，下次直接读 | 可能丢失细节，低频但关键的模式被平均掉 |
| **方案 B：向量 RAG** | 历史记录做 embedding，诊断时语义检索 | 需要额外基础设施 |
| **方案 C：知识图谱驱动** | 直接用知识图谱节点 ID 查历史（精确匹配） | 只能查同知识点，查不到跨知识点模式 |

初步倾向是 **方案 C + 方案 B**——知识图谱做精确匹配，向量做语义检索优化。

### Step 3：五维框架的 T 维度把 RAG 变成了必须

继续深入讨论时，一个关键认识出现了：

> **五维框架里有 T 维度（迁移能力），它评估的是"模型思想"——学生能否识别表面不同但内核相同的题目。**

判断"模型思想"天然需要**语义模糊匹配**：

```
❌ "这道题是分段函数" → 按知识点 ID 精确查找
   → 只能找到同样标了"分段函数"的历史
   → 发现不了"绝对值分类讨论"的关联

✅ "这道题需要分类讨论的思维" → 语义检索
   → 能找到"绝对值分类讨论"、"含参不等式讨论"
   → 结论：不是分段函数不会，是分类讨论的思维模型没建立
```

**一旦 T 维度需要评估模型思想，RAG 就不是"可选的优化"——它是必须的。**

### Step 4：自然演进的结论

```
五维框架的 T 维度需要评估"模型思想"
        ↓
"模型思想"的判断依赖"同类题"的语义检索
        ↓
"同类题"不能靠知识点 ID 精确匹配（语义模糊）
        ↓
自然地引出 RAG 向量检索
```

这个推导过程反过来也成立、且更清晰：

```
需求：T 维度（迁移能力）
  → 需要：模型思想判断
    → 需要：同类题语义检索
      → 需要：向量/RAG
        → 基础设施：轻量向量库
```

RAG 不是"看别人有所以我们也加一个"，它是从五维框架的评测需求里**长出来的**。先有问题，再有工具。

### 关于"小程序内做向量查询"的澄清

向量检索的代码逻辑跑在**云函数**侧（跟 Flash 同一侧），不是在小程序前端。小程序前端只负责调用「生成报告」和展示进度状态。具体实现方式待决策点 A 讨论确定。

## 三、独立决策点

### 决策点 A：向量检索方案

**背景**：T 维度（迁移能力）需要评估"模型思想"——即判断学生能否识别表面不同但内核相同的题目。这要求语义模糊检索，无法用知识图谱节点 ID 精确匹配。因此需要在诊断引擎中引入 RAG。

**具体场景**：
```
当前题目：分段函数求值（标注知识点：分段函数）
RAG 检索发现：过往同类错题中有"绝对值分类讨论"、"含参不等式讨论"
             → 表面知识点不同，但思维模型都是"分类讨论"
结论：该生不是分段函数不会，是分类讨论这个思维模型没建立
```

**需要讨论的子项：**

| 子项 | 选项 |
|------|------|
| 子项 | 决策 | 选项参考 |
|------|------|---------|
| A1. 向量库方案 | ✅ **已定：轻量自建**（embedding 存 mastery_logs 同一条记录，云函数内 cosine similarity 计算） | ① 自建轻量（选定） ② 第三方向量数据库 ③ CloudBase 内嵌方案 |
| A2. Embedding 模型 | ✅ **已定：text-embedding-v4**（阿里云通义千问） | ¥0.50/百万 tokens，维度 64-2048 可调，OpenAI 兼容格式 |
| A3. 存储位置 | ✅ **已定：存 mastery_logs 同一条记录** | ① embedding 直接存 MongoDB（mastery_logs 集合内，选定） ② 单独建向量集合 ③ 用外部向量库 |
| A4. 检索触发时机 | ✅ **已定：每次生成报告时实时计算** | ① 每次生成报告时实时计算（选定，~7200条/学期无缓存必要） ② 预计算+缓存 ③ 增量异步更新 |
| A5. 检索数量 | ✅ **已定：top-K = 5** | 预估 3-10 条之间，选定 5 |

---

### 决策点 B：图像理解模型部署方式

**背景**：Qwen3.7Plus（多模态，支持图片输入）作为图像理解模型。CloudBase 原生模型托管不包含 Qwen 系列。

**需要讨论的子项：**

| 子项 | 选项 |
|------|------|
| B1. Qwen 部署方式 | ✅ **已定：云函数 HTTP 调用阿里 API** | ① 云函数内 HTTP 调用 Qwen API（选定，按调用付费免部署） ② Qwen 部署到云函数 ③ CloudRun 容器 ④ API 网关+模型服务 |
| B2. 替代方案 | ✅ **已定：不启用**（保持 Qwen3.7Plus） | ① Hunyuan 多模态 ② GLM-5V（如 Qwen 成本过高才考虑，当前已选 Qwen） |
| B3. 冷启动优化 | ✅ **已定：接受冷启动延迟**（MVP 不预热） | ① 预留实例常驻 ② 异步 warm-up ③ 接受冷启动延迟（选定） |
| B4. Qwen prompt 设计 | 🟡 设计工作（进入详细设计做） | prompt 引导模型"整体把握图片"，不仅 OCR 还要观察做题痕迹（涂改、草稿、答题路径）。详细设计阶段产出 prompt 原型测试 |

---

### 决策点 C：推理诊断模型选型

**背景**：推理阶段需要较强的分析能力，但不需要多模态。CloudBase TokenHub 已支持多种纯文本模型。

**需要讨论的子项：**

| 子项 | 选项 |
|------|------|
| C1. 主模型选择 | ✅ **已定：DeepSeek V4 Flash（max 思考档）** | ① DeepSeek V4 Flash（选定） ② DeepSeek V3.2 ③ Hunyuan 2.0 ④ GLM-5 / Kimi |
| C2. Token 用量预估 | ✅ **已确认可接受** | ~8-10K tokens/次（Qwen 1-2K + 图谱历史 2-3K + RAG 3K + prompt 1K），用户已确认预算 |
| C3. 模型切换策略 | ✅ **已定：固定 Flash max，不切换** | ① 固定用 Flash（选定） ② 复杂诊断升级 ③ 用户自选 |
| C4. 云函数超时 | ✅ **已定：120s** | 预估 60-120s，选定 120s |

---

### 决策点 D：数据模型设计

**背景**：需要新增/修改数据库集合来支持诊断引擎。

**需要讨论的子项：**

| 子项 | 选项 |
|------|------|
| D1. questions 集合 | ✅ **已定：独立集合** | ① 独立集合（选定，每道题一条记录，关联知识点 ID） ② 嵌入诊断记录 ③ 引用 NoSQL |
| D2. mastery_logs 集合结构 | ✅ **已定：每次诊断一条**（含五维快照+算法版本） | ① 每次诊断一条（选定） ② 每个知识点一条 ③ 两种并存 |
| D3. 向量字段存放 | ✅ **已定：存 mastery_logs 每条记录中** | ① embedding 作为字段存 mastery_logs（选定，同 A1/A3） ② 单独建向量集合 ③ 实时调用 |
| D4. 数据量预估 | ✅ **已定：无需分表/归档** | 7200 条/学期，NoSQL 无压力 |

### 决策点 E：前端交互设计

**背景**：前端需要配合诊断管线的异步特性做交互。

**需要讨论的子项：**

| 子项 | 选项 |
|------|------|
| E1. 进度展示 | ✅ **已定：两阶段文字** `ai分析中(预计耗时)` → `ai生成报告中(预计耗时)` | ① 简单文字状态（选定，增强为带预计耗时） ② 百分比进度条 ③ 仅 loading |
| E2. 批量上传交互 | ✅ **已定：拍完一批 → 点「完成」→ 统一分析出单次报告** | ① 上传列表+删除重拍 ② 单张上传最后统一出报告（选定） ③ 先拍完再选 |
| E3. 诊断报告展示 | ✅ **已定：小程序内展示 + 分享链接** | ① 小程序内展示（选定，五层结构） ② PDF/图片 ③ 服务通知 |
| E4. 错误处理 | ✅ **已定：失败标记+原图展示+引导重新上传** | ① 某张失败不阻塞整批（选定） ② 整体重试 ③ 局部重试（重传单张） |
