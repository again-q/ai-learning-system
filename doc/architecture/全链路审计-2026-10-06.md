## 二、🔴 有实际影响的问题（2 处）

### 2.1 图谱页用**失效的 mastery 字段**上色 —— 28/52 行颜色是错的

**证据链**：
```
graphService/index.js:47   progressMap[p.knowledgeNodeId] = p.mastery      ← 读 mastery 字段
graph.js:71                 mastery: Math.round(progressMap[knowledgeId] * 100)  ← ×100 上色
```

**问题**：决策 052 之后 K 的权威口径是 `correctCount / attempts`，
但 `knowledge_progress` 里有 **28/52 行的 `mastery` 是旧口径残留**，两者不一致：

| 节点 | 图谱页显示 | 052 口径应为 |
|---|---|---|
| math_10_ch0_s2_000 | 0.57 | **0.333** |
| math_10_ch1_s1_001 | 0.71 | **0.667** |
| math_10_ch1_s1_004 | 0.36 | **0.273** |
| math_10_ch1_s2_004 | 0.60 | **0.545** |

**影响**：学生看到的掌握度颜色**偏乐观**（0.57 vs 0.33 会跨过 50% 阈值）。

**同类问题我今天已在 `statService` 修过**（新增 `rowK`）。但 `statService` 没有调用者（见 3.4），
**真正在展示 K 的是 `graphService`，那里还没修。**

**修法**：`graphService` 的 `progressMap` 改为按 052 口径重算：
```js
progressMap[p.knowledgeNodeId] = attempts > 0 ? correctCount / attempts : null;
```
（或直接复用 `shared/reportReadings.hitRateOf`，但它没有 052 的 evidence 语义；
`statService/kFormula.rowK` 更贴切，但跨云函数不能 require，需走 `shared/` 分发。）

### 2.2 决策 063 的 A/U **写进库了，但没有任何地方展示**

**证据**：
```
unit_progress 的写入方：
  updateMastery.js  (graphEngine)         ✅ 写 λA/λU/aValue/aUpper/aLevel/aD/uD
  judgeOne/updateMastery.js               ⚠️ 旧 055 算法，且是死代码
unit_progress 的读取方：

  ragService/index.js:249    getUnitLevel                          ← 无人调用
前端：grep aValue|aUpper|lambdaA|lambdaU|aLevel miniprogram → **0 命中**
```

**影响**：**A（实际发挥）/ U（能力前沿）目前只进不出。**
我今天做的 063 落地（λ 轴、五情况、14 项单测、真实 59 题验证）**在用户侧零可见效果**。

**这不是"白做"** —— 代码正确、测试齐、报告侧快照也落库了，**缺的是最后一段展示**。
但必须如实说明：**当前 A/U 对学生不可见。**

## 三、🟡 写了没人读 / 死代码（7 处）

### 3.1 `ragService.getNodeHistory` 的节点过滤**被静默丢弃**（真 bug，但在死路径上）

```js
// ragService/index.js:50
async function fetchLogs(userId, days) { ... }          // ← 只有 2 个参数
// ragService/index.js:226
const logs = await fetchLogs(userId, days, { knowledgeNodeId: nodeId });
//                                  ↑ 第三个参数被忽略
```

**后果**：`getNodeHistory` 返回的是**该用户全部知识点的掌握度变更历史**，而不是请求的那个节点的。
`node`（当前状态）是对的，`logs`（历史）是错的。

**为什么没爆**：`getNodeHistory` 只被 `toolLoop` 调用，而 `toolLoop` 从未被调用（见 3.5）。

### 3.2 `statService` **无任何调用者**

```
statService.overview / patternTrajectory   ← 全仓 0 处调用
```
我今天在 `masteryOverview` 修的"最弱知识点排序"是真 bug，但**修在了死代码上**。
（`reportService/assemble.js:22` 注释说"与 statService 逻辑一致；函数内联避免跨函数调用延迟"——
所以线上走的是**内联副本**，不是 statService。）

### 3.3 `report.unitLevels` 写了没人读
后端 `reportService` 把单元级 A/U 快照写进报告对象，前端 `grep unitLevels miniprogram` → 0 命中。

### 3.4 `progressDetail` 后端给了前端没用
`graphService` 返回 `progressDetail`（含 `evidence`/`aggregated`，决策 052/056 为"样本不足别显示 0%"而加），
前端只用了 `progressMap`，**`progressDetail` 0 处引用**。

### 3.5 `toolLoop` / V3 报告路径整体未启用
```js
reportService/index.js:9   const { runWithTools } = require('./toolLoop');   // 引入了
                           但全文件无调用 → toolLoop 及它带动的 4 个 ragService 工具全是死代码
reportService/index.js:6   const SYSTEM_V3 = require('./systemV3');          // 同样只引入未使用
```
所以 `getErrorPattern`/`getTrend`/`getNodeHistory`/`getUnitLevel` 四个工具**都无消费者**。

### 3.6 `judgeOne/updateMastery.js` 是死代码
`judgeOne` 现在只有 4 个 action：`listQuestions` / `updateTranscription` /
`reviseByNaturalLanguage` / `updateParams` —— **没有 `judge`**。
判定已整体搬到 `graphEngine`。
**好消息**：它写的还是旧 055 算法的 A，因为不执行，**不会与新的 063 打架**。

### 3.7 `questions.status` 字段是死的
`diagnose` 写入 `'pending'`，之后**无人更新**；真实数据分布 `{undefined:38, pending:23}`。
报告里的三态是 `assemble.js:70` **自己从 processScore 推的**（不读这个字段），所以**不影响展示**；
但字段本身是遗留噪声，容易误导（我审计时差点据此误报一个"报告全显示待判"的假 bug）。

## 四、⚪ 一致性 / 健壮性（2 处）

### 4.1 小程序 33 个 `callFunction` 只有 11 个检查返回码

`wx.cloud.callFunction` **不会因返回体里的非 0 code 而 reject**。
今天已修**唯一会返回 503 的那处**（`review.js` 的 `judgeQuestion`），其余 22 处未动。
（其中 12 处是 lang/highlight 之类的非业务调用，实际业务调用约 10 处。）

### 4.2 `mastery_logs` 一个集合装**两种行形状**

```
N6 ragLog 行        : { questionId, pattern, report, isCorrect, processScore, embedding … }
updateMastery 行    : { triggerQuestionId, knowledgeNodeId, oldMastery, newMastery … }
```
只靠"哪些字段存在"区分。**3.1 那个 bug 就是踩了这个坑**（按 `newMastery != null` 过滤时，
如果不先按节点过滤，就会混进所有节点的记录）。

建议：给两类行加一个显式的 `kind: 'rag' | 'k-change'` 字段，让区分**显式化**。
