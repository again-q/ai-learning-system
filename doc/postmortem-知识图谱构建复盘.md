## 1. 项目概况

**目标**：将整本人教A版高中数学必修第一册教材（267页，24节）转化为结构化知识图谱 JSON，用于 AI 学习助手小程序的五维诊断。

**最终产出**：24 个独立 JSON 文件，359 知识点节点，存放于 `knowledge-graph/`。

## 3. 踩坑记录

### 3.1 🔴 TOC页码偏移（最高成本）

**现象**：TOC 记录的是教材印刷页码，但 PDF 物理页码偏移了 +6。第1页PDF物理页是封面，正文从第7页开始。

**影响**：直接按印刷页码跑 OCR，产出了 155 页全错的内容，全部重跑。

**根因**：没有做最基本的"第一页内容验证"。

**修复**：用 PyMuPDF 读取 PDF 页数，OCR 目录页，对比目录内容确认偏移量。

**预防清单**：
```
□ OCR前：PyMuPDF确认PDF总页数
□ OCR前：OCR目录前3页，验证章节标题匹配
□ OCR中：每5页检查一次OCR内容是否连续
□ OCR后：抽样验证首尾页内容
```

### 3.2 🔴 JSON 内引号问题（频率最高）

**现象**：Agent 2 和 Agent 3 输出的 JSON 在字符串值中内嵌了 ASCII 双引号，导致 JSON 解析失败。

**示例**：
```json
"summary": "并集的核心逻辑词是"或"（element-wise OR）"
```
这里的 `"或"` 使用了 ASCII `"`，JSON 解析器看到第一个 `"` 就认为字符串结束了。

**影响范围**：最终修复了约 10 处，涉及 4 个 JSON 文件（4.4、4.2、5.6、1.3）。

**根因**：大模型训练数据中的中文文本使用 `"` 作为引号，模型没有将其转义为 `「」` 的意识。

**修复方案**：
```python
# 方案A：精准替换（推荐）
raw = raw.replace(chr(0x22) + '补集' + chr(0x22), '「补集」')

# 方案B：正则批量（有风险）
import re
raw = re.sub(r'(?<=[\u4e00-\u9fff])"([^"]{1,60}?)"(?=[\u4e00-\u9fff])',
             r'「\1」', raw)
```

**预防**：在 Agent Prompt 中明确写死：
```
⚠️ JSON 字符串值内部禁止使用未转义的 ASCII 双引号（"）。
中文引用请使用「」（直角引号）或删除引号。
错误示例：{"name": "称为"补集""}
正确示例：{"name": "称为「补集」"}
```

### 3.3 🟡 section_id 命名不一致

**现象**：同一节在不同阶段的文件名格式不同。

| 阶段 | 文件名 | 格式问题 |
|------|--------|---------|
| OCR 输出 | `math_10_ch1_4_充分条件与必要条件.txt` | `_s` vs `_` |
| Agent 1 产出 | `math_10_ch1_4_充分条件与必要条件.md` | 同 OCR |
| Agent 2 期望 | `math_10_ch1_s4.json` | 用 `_s` 格式 |

**影响**：pipeline 跳过已完成的逻辑失败，重复跑了已完成的节。

**修复**：脚本中用 `cut -d'_' -f1-4` 提取纯 section_id。

**教训**：命名规范应在一开始就定死，所有阶段使用同一个 section_id。

### 3.4 🟡 schema 漂移

**现象**：有的节使用旧 schema，有的使用 Agent 自行决定的新 schema，质检 Agent 统一用旧 schema 校验，导致新 schema 的节被标记为"质量差"。

**旧 schema**：
```json
{"knowledge_id": "...", "basic": {"name": "...", "type": "..."}, ...}
```

**新 schema**（Agent 擅自改变）：
```json
{"id": "...", "title": "...", "content": "...", "key_terms": [...], ...}
```

**预防**：Agent Prompt 必须附带 JSON schema 的完整示例，并强调"严格按照此格式输出，不得增删字段或改变结构"。

### 3.5 🟡 type 类型不规范

**现象**：Agent 2 输出的 `type` 字段使用了约 15 种非标准值（`concept`, `theorem`, `meta`, `overview`, `application`, `skill`, `model`, `explore`, `history`, `connection`, `extension`, `proposition`, `thought`, `background`, `meta_concept`）。

**标准类型**：`definition`, `property`, `notation`, `method`, `example`（5 种）。

**修复**：建立 type 映射表批量替换。

**教训**：标准 type 列表必须在 Prompt 中明确给出，不是"可以参考"而是"必须使用这5种"。

### 3.6 🟢 文件重组时机

**经验**：先跑完所有节再整理文件结构，避免搬动过程中遗漏新生成的节点文件。s4 就是这样丢失的——文件重组时 4.4 还没跑完，后面跑完了但没搬过去。

## 4. 成功经验

### 4.1 🟢 三 Agent 管线设计正确

- **A1 版面分析**：把 OCR 原始文本转为结构清晰的 Markdown，标题层级正确、公式/例题/练习区分清晰
- **A2 知识点提取**：从 Markdown 中提取知识点节点，同时构建 tree 结构和 relations 关系
- **A3 质量校验**：检查阻塞问题（B1-B6）和警告（W7-W13），拦截质量问题

**平均耗时**：每节约 5-7 分钟（A1 ~2min + A2 ~2min + A3 ~2min）

### 4.2 🟢 Shell 脚本调度优于手动

- `pipeline-all.sh`：自动跳过已完成/已失败的节
- 幂等设计：检查 `knowledge_index.json` 和文件存在性
- 失败了不阻塞，记日志继续下一节

### 4.3 🟢 OCR 方案的性价比

- 腾讯云 `GeneralAccurateOCR`：267 页，0 元（免费额度）
- 置信度：封面 98%、公式 96%、正文 94-98%
- 对比：MinerU Mac 不可用，ppstructure 安装复杂，其他 OCR 无免费额度

### 4.4 🟢 补集修复流程

单节点遗漏时不需要重跑全书：
```
追加 OCR 页 → 清旧 A1/A2/A3 → 单节重跑 → 更新索引
```
15 分钟内解决，不需要动其他 23 节。

### 4.5 🟢 最终文件结构

```
knowledge-graph/          ← 纯净的知识图谱最终产出
├── knowledge_index.json  ← 一键获取全本节点
└── nodes/                ← 每节独立，方便小程序按需加载
```

## 6. 后续建议

### 6.1 对下一本教材的建议

1. **PDF 预处理**：先 OCR 目录页验证页码偏移，再开始整本 OCR
2. **Agent Prompt 加固**：
   - 明确禁止 JSON 内 ASCII 双引号
   - 附带完整 JSON schema 示例
   - 限定 type 为 5 种标准值
3. **文件命名**：section_id 格式从第一天统一，不要混用
4. **先试跑**：先跑 1 节验证全流程，确认没问题了再批量跑
5. **节点上下限**：不设硬限制，让 Agent 自由判断

### 6.2 质量提升方向

- **跨节引用**：当前 relations 主要在同一节内，跨节引用需要后处理补充
- **`importance` 权重**：当前全部预设 3（中），后续可用历年高考题反推
- **`level` 分层**：当前全部 `knowledge`，后续可引入 `model`（模型层）和 `method`（方法层）

### 6.3 工具链改进

- **JSON 后处理脚本**：建立标准修复流水线（type 映射 + 内引号修复 + ID 去 `__` + 引用验证）
- **增量索引更新**：重跑单节后自动更新 `knowledge_index.json`，不手动编辑
- **质检报告持久化**：每次质检保存历史，便于追溯

## 7. 每个 Agent 的改进建议

### 7.1 Agent 1（版面分析）改进

**当前问题**：
- 有时返回空（4.2~4.4 初次跑时），原因不明
- Markdown 结构不稳定：标题层级有时用 `#` 有时用 `##`，公式格式不统一
- 节末尾的 OCR 页脚文字（如 "12第一章集合与常用逻辑用语"）有时被保留有时被清理

**改进方案**：
```yaml
prompt_加固:
  - 输出格式锁定为: "# 章节标题\n\n## 小节标题\n\n正文...\n\n### 例题\n\n..."
  - 公式统一用 $$ ... $$ 独立行，行内公式用 $...$
  - 页脚文字（页码+章节名）必须清除
  - 如果输入内容不足一页或不完整，输出 "INPUT_INCOMPLETE" 而不是空响应
retry_策略:
  - 空响应时自动重试 1 次（当前脚本不重试直接跳过）
  - 重试仍空则记录到 _failed.log
```

### 7.2 Agent 2（知识点提取）改进

**当前问题**：
- JSON 内 ASCII 双引号（频率最高的问题）
- type 字段用了 15 种非标准值
- schema 格式不统一（新旧混用）
- 跨节引用 ID 有时写成 `math_10_ch2_s2` 缺少具体节点 ID
- 节点 ID 偶发 `__` 双下划线

**改进方案**：
```yaml
prompt_加固:
  - ⚠️ JSON 字符串值内部禁止使用未转义的 ASCII 双引号（"），中文引用请用「」
  - type 只能取以下 5 种之一：definition、property、notation、method、example
  - 严格按此 schema 输出，不得增减字段：
    {\"knowledge_id\": \"...\", \"basic\": {\"name\": \"...\", \"type\": \"...\", ...}, ...}
  - knowledge_id 使用单下划线分隔，禁止 __
  - relations.reference 必须指向具体的节点 ID，不是节 ID
后处理_防御:
  - 即使 Prompt 加固了，仍建议在脚本层做二次校验：
    - JSON.parse 失败 → 自动修复内引号 → 重解析
    - type 非标准 → 映射表转换
    - __ → _ 替换
```

### 7.3 Agent 3（质量校验）改进

**当前问题**：
- 校验标准不统一：对旧 schema 文件和新 schema 文件用同一套规则，后者被误标记
- 有时标记"缺失内容"实际是 OCR 截断问题，不是 Agent 2 的错
- 不输出修复建议，只输出"阻塞/警告"

**改进方案**（这也是你提到的 ReAct 思路）：
```yaml
自反馈_循环:
  - A3 质检不通过时，不是直接返回"不通过"，而是：
    1. 分析问题类型（schema/type/内引号/内容缺失）
    2. 如果是可自动修复的（type/内引号），给出修复建议
    3. 如果是内容缺失，判断是 OCR 截断还是提取遗漏
    4. 标记可自动修复 vs 需人工介入
  - 质检报告增加字段：
    {\"auto_fixable\": [问题列表], \"manual_needed\": [问题列表]}
  
prompt_加固:
  - 校验时先确认 schema 版本，再按对应版本规则校验
  - 对 OCR 截断导致的"内容缺失"只记警告不记阻塞
  - 输出格式必须包含 fix_suggestion 字段
```

### 7.4 管线脚本（Shell）改进

**当前问题**：
- 不重试空响应
- 跳过逻辑基于文件名匹配，容易因命名不一致而失败
- 每节串行跑，24 节需要 ~6 小时

**改进方案**：
```yaml
重试机制:
  - Agent 返回空 → 自动重试 1 次
  - 重试仍空 → 记 _failed.log → 继续下一节
  - Agent 输出 JSON 损坏 → 自动修复后重解析 → 仍坏则重跑

幂等增强:
  - 跳过条件同时检查：knowledge_index 索引 + 文件存在性 + 文件校验和
  - section_id 统一提取：basename → cut -d'_' -f1-4

并行加速（可选）:
  - 当前串行：24节 × 5-7min = ~6h
  - 可并行 3 路（互不依赖）：8节/路 = ~2h
  - 注意：knowledge_index.json 需要最终合并
```

## 8. 理想管线设计（v2.0 目标）

```
┌─────────────────────────────────────────────────┐
│                   pipeline-v2.sh                 │
├─────────────────────────────────────────────────┤
│                                                   │
│  for 每节:                                        │
│    ├─ OCR 验证（页数/内容完整性）                  │
│    ├─ A1: 版面分析                                │
│    │   └─ 空响应? → 重试1次 → 仍空? → 记失败     │
│    ├─ A2: 知识点提取                              │
│    │   ├─ JSON解析成功? → 校验 schema + type      │
│    │   ├─ 失败? → 自动修复内引号 → 重解析         │
│    │   └─ 仍失败? → 重跑 A2                      │
│    ├─ A3: 质量校验 + ReAct 自反馈                 │
│    │   ├─ 通过? → ✅ 入库                        │
│    │   ├─ 有可自动修复项? → 修复 → 重新校验       │
│    │   └─ 有需人工项? → 记 _needs_review.log      │
│    ├─ 后处理: type映射 / ID清理 / 引用验证        │
│    └─ 入库: knowledge-graph/ + 更新索引           │
│                                                   │
│  失败管理: _failed.log → 人工审查 → 批量重跑       │
│  并行: 3路并行, 最终索引合并                       │
└─────────────────────────────────────────────────┘
```

**关键改进**（对比 v1）：
1. A2 输出自动 JSON 修复 → 减少人工介入
2. A3 自反馈循环 → 质量问题在管线内闭环
3. 重试机制 → 空响应不直接跳过
4. 并行 → 提速 3x
5. 验收标准统一 → 不再因 schema 漂移误判
